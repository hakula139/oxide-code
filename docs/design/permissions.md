# Tool Permissions and Approval

Every tool call passes through a permission gate. Rules place calls in one of three tiers: deny, ask, or allow. The mode decides the calls the rules leave open, and `plan` also denies every `edit`, `exec`, and `net` call. [Permissions](../guide/permissions.md) covers the modes, the rule syntax, the built-in rules, and the settings for users, and this page covers how the gate reaches each decision.

Companion docs: [Modals](modals.md), [File Edits](file-edits.md).

## Rules and Classes

Rules live in three tables under `[permission]`, one for each tier, and each table holds a pattern list for each permission class: `read`, `edit`, `exec`, `net`, and `mcp`. Each tool declares its class in its `ToolSpec`, and `Tool::spec` has no default, so a new tool cannot inherit a permissive class. No built-in tool belongs to `net` or `mcp` yet, so those lists parse and validate but match no calls, and MCP tools join `mcp` with [#178](https://github.com/hakula139/oxide-code/issues/178).

A `Rule` pairs a class with a pattern, and the list that holds it sets its tier. Every pattern compiles when the config loads, so a malformed pattern fails startup and names its file.

The mode resolves from `permission.mode`, then `OX_PERMISSION_MODE`, which treats an empty value as absent and fails on a typo as `effort` does, then `--mode`, which `/config` credits to the flag. Each config layer appends its `permission.<tier>.<class>` lists and `extra_roots`, while a higher layer's `permission.defaults` key replaces a lower one, and the merge records each entry's layer for `/config`. A project's `.ox/config.toml` may set only `deny` and `ask` in `[permission]`, which `reject_project_keys` enforces (**Project files tighten only**).

## Decision Pipeline

Before the gate, `Tool::prepare` parses the call's input and rejects a missing, mistyped, or unknown field and input `edit` or `tasks` can never run, such as an `edit` whose `old_string` and `new_string` are identical, so a rejected call ends with that error and never asks. `grep` and `glob` compile their patterns when they run, so an invalid pattern fails after the gate.

The gate evaluates each call in a fixed order and stops at the first match.

1. **Deny tier** → deny. A deny rule for the call's class matches, or a `bash` command writes a file a deny `edit` rule matches or reads for certain a file a deny `read` rule matches.
2. **`plan`** → deny an `edit`, `exec`, or `net` call.
3. **Ask tier** → ask. An ask rule matches, an edit-class call targets a protected path, or a `bash` command holds syntax the analysis does not recognize, writes a file an ask `edit` rule matches or a protected path, reads for certain a file an ask `read` rule matches, may read a file a deny or ask `read` rule matches, or, while the `rm` default is on, runs a forced recursive `rm`. In `yolo`, only a configured ask rule asks here (**Deny rules and the user's ask rules hold in every mode, and `yolo` skips ox's own asks**).
4. **Read-class call** → allow.
5. **Edit-class call inside the workspace** → allow.
6. **Allow tier** → allow. An allow rule or session grant matches the call.
7. **Mode** → allow in `yolo`, and ask in `manual` and `plan`.

Deny rules outrank every ask and allow rule, and ask rules outrank every allow rule, session grant, and the defaults at steps 4 and 5 (**Ask outranks allow**). A `bash` command reaches step 6 only if the analysis recognizes all of it, every simple command in it is allowed by an `exec` rule or is a known-safe read, and every file it writes is inside the workspace or allowed by an `edit` rule.

Each step settles the call with a `Verdict`, which pairs the `Decision` with the `Basis` that reached it, such as a configured rule and its tier, the built-in group behind a shipped pattern or protected path, a session grant, a default, the mode, or the first construct the analysis does not recognize (**Every decision names its basis**). The gate logs every verdict at debug level, a denial names its basis in the result the model reads, and the approval prompt names the rule that made the call ask.

A call that would ask in a run nobody attends settles as `Decision::Unapproved`, and the gate denies it without a request (**Attendance is an engine setting**). Its result says why the call needs approval, tells the model not to retry it as written, and names the next step as a request to the user, since the model should not edit the user config to get past a denial. A call no rule settles names the allow pattern that would admit it, taken from its session grant. For a call a built-in ask group holds, `Policy::config_fix` evaluates the call again with that group off and names the `[permission.defaults]` key only when the call would then run. A read the `ssh` or `credentials` deny group guards names the group without suggesting that the user disable it.

## Path Targets

A path tool resolves its target before any rule runs, in `Tool::prepare`, against the session's `Workspace` in its `ToolCtx`. `Access::for_path` expands a leading `~`, joins the path to the cwd, and walks it one component at a time as the kernel does, following every symlink, dangling ones included, and applying `..` from the current position, so a `missing/..` detour cannot hide a later symlink. Past the first missing component, the rest applies as `create_dir_all` builds it. A walk that cannot finish, or a resolved path that is not UTF-8, leaves the target outside the workspace under its joined spelling.

An approval names the resolved path, in the title for `edit` and `write` and in the body for `read`, as do the tool's messages, and the file tools open `Access::resolved()`, the path the gate checked (**Resolve once, act on the result**). The file tools open with no-follow flags, so a symlink swapped into the final component fails the open, and they check size and type on the opened file. `grep` and `glob` keep the path as written, since read deny rules match that spelling, and walk from the resolved root.

Each resolved target falls in one zone:

- **Protected**: an edit-class call asks at step 3 if the target's resolved or call-spelled path contains a protected name from an enabled shipped group, or sits where such a name directly inside the cwd or a workspace root resolves, so `.vscode -> tools/vscode` protects `tools/vscode` too. Names compare folded, as the file systems ox runs on compare them: case, default-ignorable code points, trailing dots and spaces, and on Windows 8.3 short names and NTFS stream suffixes.
- **Workspace**: an edit-class call is allowed at step 5 when the target sits inside a workspace root, the cwd or a `permission.extra_roots` entry. A cwd of `/`, `$HOME`, or an ancestor of `$HOME` gives the workspace no roots. The check compares file identity, so directory aliases count as the directory they name, and a regular file with more than one hard link is never a workspace target, since another link can sit outside every root.
- **Outside**: every other target needs an allow rule, approval, or `yolo`.

`Access::Path` records the protected names a target contains by group, so the policy applies the groups the config enables without resolving the path again.

## Command Targets

A `bash` call's target is its command as tree-sitter-bash parses it. `Access::for_command` splits it into simple commands across lists, pipelines, subshells, and compound statements, and turns each output redirection to a file into an edit-class path target and each input redirection into a read-class one, resolved and zoned like a path tool's target. The `permission/shell.rs` module docs and constants hold the enumerations: the wrappers and their option grammars, the recognized node kinds and builtins, the variables a command may set, the known-safe commands, and the readers.

- **Words.** Rules compare parsed words, unquoted and with `$'...'` decoded, so quoting and spacing do not change what a rule sees (**Words over strings**). A word that expands or globs stays marked, so an allow pattern can refuse it and a deny pattern can treat it as any word.
- **Wrappers.** Each simple command drops the wrappers that lead it, parsing each wrapper's options by its own grammar. Deny and ask rules see the command every wrapper runs, while allow rules see through only the wrappers that change how a command runs, such as `nice` and `timeout`, and not those that change who runs it or with which arguments, such as `sudo` and `xargs` (**Rules follow command runners, and allow rules see through only the harmless ones**). A leading assignment outside the short list of output-only variables stays part of what an allow rule must name.
- **Recognized syntax.** The analysis recognizes a command by an allowlist over tree-sitter-bash's syntax. A command holding anything outside it, such as arithmetic, a function definition, a write to a variable a later program may read, or a word the grammar ends where bash does not, is unrecognized: a deny or ask rule may still match what the analysis sees, but no allow rule covers it (**The analysis recognizes syntax by an allowlist, and an unrecognized command asks in `manual` while `yolo` runs it**, **A command may write only a local name or an output variable**).
- **Nested commands.** The analysis looks for a command inside another only through the wrappers, `find`'s `-exec` family, command and process substitutions, and the literal script of a shell's `-c`, `eval`, `su`, or `runuser`. Every rule sees those commands, and an allow rule must still cover the shell or runner itself. Any other runner, such as `watch`, `make`, or `python3 -c`, is the program rules see.
- **Known-safe reads.** A short list of read-only commands runs without an allow rule when every argument is a literal word without globs, the command runs under its bare name, and nothing in the whole command expands a variable. Commands that can do more carry guards, such as `sed` without `-i` or a script file, and `find` without an action that runs, deletes, or writes.
- **Readers.** The commands that read their file operands, such as `cat`, `grep`, and `find`, are weighed against `read` rules whether or not a call is safe. Each reader's option grammar sorts its words into options, values, and files, counting every file any supported build or option order would read. A literal file every build reads, or the root of a tree a recursive reader traverses, is a certain read that the deny and ask tiers weigh as an input redirection, while a file below that root, a word that expands, and a glob whose roles stay unknown are possible reads (**A reader's certain reads face the deny tier, and its possible reads ask outside `yolo`**). A tree is held when its root and a rule's literal prefix are ancestors of one another, without enumerating files, and links below the root are not followed ([#658](https://github.com/hakula139/oxide-code/issues/658)).
- **Directory changes.** A program reads the directory it runs in, so after a directory change that may leave the workspace, no rule allows the rest of the command. Only a first `cd` or `pushd` to one literal directory inside a workspace root stays inside, and a directory change beside a redirection, a reader of a relative path, or a program spelled with a relative path leaves the command unrecognized, since that path may then name another file (**Rules allow nothing that runs after a directory change the gate cannot place**). The deny and ask tiers still weigh a relative reader operand, glob, or redirection target under the working directory and under every directory a `cd` or `pushd` with one literal target, or a bare `cd`, may have entered, keeping the earlier ones in case a change fails, so `cd ~/.ssh && cat id_rsa` is a read of `~/.ssh/id_rsa` in every mode. After a change the analysis cannot spell, such as `cd $DIR`, `cd -`, or `popd`, a relative reader operand may name any file. `CDPATH` needs no handling, since [`bash`](bash.md) drops it from the command's environment.

## Patterns

[Rules](../guide/permissions.md#rules) gives the user-facing grammar. Allow rules widen what can run, so they match conservatively, while deny and ask rules hold calls back, so they match across every spelling a call can have. `MatchDiscipline` carries the two approaches, and the ask tier uses the deny one.

An allow `exec` pattern matches a simple command's named words exactly, with a `*` before the last word matching one word that neither expands nor globs and a trailing `*` matching the rest, so `cargo test *` never covers `cargo test && rm -rf /`. A deny or ask `exec` pattern matches the named words, the program words, or the program words with the program's directory dropped, compares words folded, and needs its later words only in order, with any words between, so `rm -rf *` stops `/bin/rm -rf x`, `RM -RF x`, and `FOO=1 nice rm -rf x`.

`read` and `edit` patterns work like `.gitignore` entries, anchored at each anchor directory, the cwd and each workspace root, unless they start with `/` or `~/` (**Gitignore-style paths**). An allow pattern matches the resolved path. A deny or ask pattern also matches the path as the call spells it and through directory aliases, compares names folded as protected paths do, and matches beneath each pattern's literal prefix both as written and as it resolved when the policy loaded, so `.env -> ../shared/.env` cannot route a read around `deny.read = [".env"]` (**Deny and ask rules are the enforced boundary for path tools**).

## Shipped Defaults

oxide-code ships named groups of rules in the deny and ask tiers, which the [built-in rules](../guide/permissions.md#built-in-rules) list, and `permission/defaults.rs` holds. The groups that ask about edits define the protected names and home locations of the Protected zone, each covering files that can run or configure code outside the task at hand (**Protected paths ask**). No group joins the allow tier, so an allow rule never overrides one, and a user config turns a group off with `false` under `[permission.defaults]`. A `read` deny group also withholds its files from `grep` and `glob` walks.

## Approval Round-Trip

When the gate asks, the decision travels through the `ops` channel the turn loop polls (**Approval decisions on the op channel**). `run_tool_round` gates calls one at a time, so at most one approval is outstanding, and runs consecutive parallel-safe calls, the read-only `read`, `grep`, and `glob` tools, together once each passes the gate, so an approval never waits on a running call.

For a call that asks, the dispatcher emits `Event::ApprovalRequested` with the call's ID, the basis that made it ask, a session grant, and a preview: an edit diff, a diff against the current content for `write`, or the command for `bash`. `await_approval` waits through `Mailbox::race_or` as the turn's other waits do, so an interrupt or shutdown ends the wait and a queued prompt or mode switch waits in the `Mailbox`, and it matches `Op::Resolve` by ID. Every frontend answers with an `ApprovalDecision`: `Approve`, `AllowForSession`, `Deny`, `DenyWithFeedback`, which returns the user's text to the model, or `Abort`, which ends the turn as an interrupt does.

In the TUI, an `ApprovalModal` joins the `ModalStack`, and its `on_cancel` hook resolves the call to `Abort` whenever the modal leaves without an answer, so the blocked turn always gets one. Its keys wait for a 300 ms pause before they answer, so a keystroke meant for the input box or a pasted burst cannot approve a call, and the guard restarts whenever the view changes. The preview shows everything it approves: every row wraps, a long body scrolls, control and zero-width characters render as escapes, and whitespace runs in a command render as `·`.

A session grant lets the user allow the call and every later call it covers:

- **Grant**: `Policy::session_grant` derives the narrowest rule that names the call with `Rule::for_call` and offers it only when adding it would allow the call. Protected paths, ask-rule matches, unrecognized commands, commands with several simple commands, and words that expand, glob, or hold characters the editor cannot show offer none, so the user always sees the exact rule they grant.
- **Editor**: the user can widen or narrow the pattern before accepting it, and `SessionGrant::accept` requires it to still cover the call.
- **Engine check**: a frontend's check is advisory, so the gate admits the answered rule against its own grant with `SessionGrant::admit` and denies the call if the rule fails.
- **Lifetime**: an admitted rule joins the engine's policy as an allow rule at step 6 and lives only in memory until `/clear`, `/archive`, or a successful `/resume` (**Approvals stay in process**). `Event::SessionRulesUpdated` carries the list to the frontend for `/status`.

## Stdio Frontends

The `--no-tui` REPL and `-p` headless runs share `render_op`, which passes each `Event::ApprovalRequested` to an `Approver` and sends the decision back as `Op::Resolve`, so `stream-json` output carries only the call's result. `main` calls `Config::set_unattended` for a headless run and for a REPL whose stdin is not a terminal, so piped input never answers a prompt. The REPL's prompter writes the escaped preview and the rule to stderr and reads the answer from the next stdin line. The stdio sink escapes control characters in model and tool text, so streamed text cannot redraw the terminal to disguise the preview.

## Search Walks

Read-class tools are allowed at step 4, but they still resolve a target, so a path-scoped deny or ask rule can match first. `grep` and `glob` gate on the search root, then check every file the walk finds against the `read` deny and ask rules, where it resolves and as spelled beneath the root, and withhold the matches, ending their output with a count of withheld files but no names. A walk does not follow symlinks below its resolved root, so the check needs no I/O.

## Design Decisions

1. **Deny rules and the user's ask rules hold in every mode, and `yolo` skips ox's own asks.** A mode that skipped deny rules would make a deny rule's meaning depend on a setting elsewhere, and a configured ask rule records a call the user wants to see, such as `git push`, whatever the mode. The shipped ask rules, protected paths, and the analysis's holds are ox's defaults for a watched session, and choosing `yolo` opts out of them. Claude Code's `bypassPermissions` draws the same line: it keeps deny rules, prompts for explicit ask rules, and runs writes to protected paths. It also prompts before an `rm` of a critical path such as `/` or `~`, while ox's `rm` group holds every forced recursive delete and is a guardrail (**`exec` deny rules are a guardrail**), so `yolo` skips it with the other shipped asks. Codex's `approval_policy = "never"` runs the rest inside its sandbox, which ox lacks, so `yolo`'s guardrails are the rules alone. `plan` denies `edit`, `exec`, and `net` calls ahead of the ask tier because approving one would break the read-only session.
2. **Ask outranks allow.** An ask rule records a call the user wants to see, such as `git push`, even when a broad allow covers it. Placing the ask tier above every allow, including session grants, the workspace allow, and a future classifier, preserves that request as the allows grow.
3. **Protected paths ask.** Editing `.git/hooks`, `.vscode/tasks.json`, or `.envrc` inside the workspace can escalate to code execution outside the task, so these paths ask even under `allow.edit = ["*"]`, in every mode but `yolo`. Asking keeps legitimate edits possible, while a deny would require the user to edit config, and a user who never wants to be asked about one group can turn it off.
4. **Words over strings.** Matching `exec` patterns against parsed words gives a rule the same meaning regardless of how the command quotes, spaces, or wraps its words, and lets an allow pattern reject a word that could expand into several. A lone `*` is the only wildcard, so rules do not depend on how a glob inside a word interacts with shell quoting.
5. **Gitignore-style paths.** Patterns work like `.gitignore` entries, so `.env` and `target` need no `**/` prefix and cover what is beneath them. Anchoring at every anchor directory applies a project rule to each workspace root, while `/` and `~/` keep exact absolute rules available.
6. **Resolve once, act on the result.** Resolving in `prepare` and opening `Access::resolved()` makes the tool open the path the gate checked, and a no-follow open makes a symlink swapped into the final component fail the open. A swap in an intermediate directory needs `openat`-style traversal or an OS sandbox ([#133](https://github.com/hakula139/oxide-code/issues/133)).
7. **Project files tighten only.** Honoring a project's `allow`, `mode`, `extra_roots`, or `defaults` would let a teammate's repo broaden what the local user permitted, the same privilege-escalation vector as project-set credentials. Appending `deny` and `ask` rules lets a repo restrict itself without that risk.
8. **Deny and ask rules are the enforced boundary for path tools.** The deny and ask lists match both spellings of the path as the file system sees it when the gate checks, each pattern's literal prefix as resolved when the policy loaded, and folded names. They do not cover a symlink swapped into an intermediate directory after the check or files touched by a `bash` command, so an untrusted model still needs an external OS sandbox.
9. **Approval decisions on the op channel.** Routing approvals through `ops` and the `ModalStack` reuses the turn loop's cancel, quit, and queue semantics, so approvals need no second channel or control-flow path.
10. **Every decision names its basis.** Carrying the basis with the decision lets the denial, the approval prompt, the headless reason, and the debug log all name the same rule, so the model and the user can see which rule fired, and the user knows which pattern to change.
11. **Mode switches wait for the next gated call.** `Op::SetMode` waits in the operation's `Mailbox` during a turn, a compaction, or a sign-in, the gate takes it before it weighs each call, and `Engine::serve` applies a switch still waiting once the operation ends, however it ends. A switch mid-turn changes how the remaining calls are weighed without revisiting calls that already passed the gate, which would mean cancelling a running command or a pending approval. Confirming the switch with `Event::ModeChanged` on receipt keeps the status line honest about the mode the next call meets.
12. **The keyboard cycle reaches `plan` before `yolo` and wraps at both ends.** Stepping forward from the default reaches read-only `plan` first, so the first Tab press makes the safest change. `yolo` stays in the cycle, and Shift+Tab steps backward through the same order, so either key can undo an overshoot. The footer names the mode Tab selects next, so the most permissive mode is announced before a forward press reaches it. The TUI steps from the last mode it requested, so a second press before the engine confirms the first moves on.
13. **Approvals stay in process.** A persisted grant has no disk ground truth to revalidate on resume, unlike a `FileSnapshot` rehash, so restoring it would regress trust. In keeping with [**Slash commands never write user config files**](slash-commands.md#design-decisions), session commands remain reversible, and cross-session writes wait for an explicit confirmed action.
14. **Rules follow command runners, and allow rules see through only the harmless ones.** `yolo` runs whatever no rule holds, so a deny rule that `sudo rm`, `xargs rm`, or `find -exec rm` could step around would guard little there. Deny and ask rules therefore see the command each followed wrapper or `find` action runs, and after an option the parser does not know, every word that may start it. Allow rules see through only the wrappers that change how a command runs, since `sudo` and `xargs` change who runs it and with which arguments, so allowing `rm *` must not allow either. Claude Code strips only `nice`, `nohup`, `stdbuf`, `time`, and `timeout` for its rules and matches `xargs` only without options, relying on asking for the rest, while Codex looks through `sudo` and `env` only for its forced-`rm` check.
15. **The analysis recognizes syntax by an allowlist, and an unrecognized command asks in `manual` while `yolo` runs it.** A list of dangerous constructs misses whatever it forgets, including a construct a grammar update adds, while an allowlist admits a construct only once the rules see everything it runs. tree-sitter-bash's error recovery can also fold one command's words into another's or end a word where bash does not, so the words rules see may not be the words bash runs, and an allow rule could cover a command it does not name. Asking keeps a misparse or a construct nobody judged from reaching an allow rule, at the cost of an occasional prompt for valid syntax, which the prompt makes easy to rewrite by naming the construct. `yolo` runs such a command unless a deny rule or configured ask rule matches what the analysis did see, since denying it would add nothing a guardrail can promise (**`exec` deny rules are a guardrail**) and would block valid syntax with no setting to allow it. Claude Code's analysis also asks outside an allowlist of node kinds, but treats every `eval` and `source` as a construct it cannot analyze, while ox parses a literal `eval` script and lets a rule name a sourced file, since naming the file vouches for what it runs.
16. **Attendance is an engine setting.** The policy knows whether anyone can answer and settles a call that would ask as `Unapproved`, so the engine denies it without a request and words the denial itself. A frontend reply would make every frontend without a person behind it reimplement that answer, and a request no one answers would stall the turn. Codex's `approval_policy = "never"` and Claude Code's `--permission-prompts none` likewise live in the core session config.
17. **A command may write only a local name or an output variable.** A variable bash reads, such as `PATH`, `IFS`, or an entry in `BASH_CMDS`, changes what later words run without changing the words, and an exported or inherited one such as `GIT_EDITOR` or `http_proxy` changes what a later program does. Those variables have no complete list, so the analysis admits a write only to a name nothing outside the command reads: one with a lowercase letter, which none of the variables a noninteractive bash reads has, that the environment `bash` starts with does not set. `declare`-family options that evaluate later values as arithmetic, redirect writes through a name reference, or export are unrecognized for the same reason. A leading assignment on one command reaches that command alone, so a rule that names the assignment can allow it, as in `PATH=/opt/bin make`. Claude Code likewise refuses `declare -i` and `-n`, and also `-a` and `-A`, which ox admits since it leaves array keys other than numbers unrecognized.
18. **Rules allow nothing that runs after a directory change the gate cannot place.** A program reads the directory it runs in, so `cd /tmp/evil && cargo build` runs that directory's `build.rs` under rules that name both parts. The gate places only a first `cd` or `pushd` with one literal target, since a later relative target starts wherever the first one led, and a `cd` in a loop or function body may run more than once. It refuses a `..`, which bash's `cd` applies to the spelled path while the gate resolves symlinks first. `env -C`, `sudo -D`, `pkexec`, and `find -execdir` count as leaving without resolving their targets, which costs little because agents rarely use them. A lone directory change stays allowed, since it runs nothing and each `bash` call starts a fresh shell. Claude Code likewise checks a compound command's `cd` target as a path and asks when it leaves the project.
19. **`exec` deny rules are a guardrail.** An `exec` rule, and a `read` or `edit` rule or protected path applied to a `bash` command, see every simple command and redirection the analysis finds, but no analysis of a command line can make them a boundary. A rule that names a program cannot match a copy of it under another name, as in `cp /bin/rm ./x && ./x -rf ~`, and no rule sees what a program runs or writes once it starts, such as `python3 -c`, a `build.rs`, or a git alias. Claiming a boundary would make each of these routes a vulnerability, and the list has no end. Two properties do hold, and a gap in either is a vulnerability: a `bash` command runs without asking in `manual` only when step 6 allows it, and path deny and ask rules stay a boundary for the path tools in every mode where they apply. Claude Code's bypass mode keeps deny rules but overrides its parse-failure ask, and Codex's `--yolo` keeps its exec-policy rules without a sandbox, so neither offers more.
20. **A reader's certain reads face the deny tier, and its possible reads ask outside `yolo`.** A deny rule's meaning should not depend on the mode, so `cat ~/.ssh/id_rsa` is denied in `manual` as `cat < ~/.ssh/id_rsa` is, where a prompt would offer to approve a read the `read` tool denies. A rule that matches a directory covers everything below it, so the root of a tree a reader traverses is a certain read. A file below that root, a word that expands, and a glob whose roles stay unknown only may reach a held file, and a rule with a broad prefix such as `/**/.env` may match below every directory, so treating them as certain would deny `find .` and `grep -r TODO src` under that rule. A guardrail that denies safe reads teaches users to drop the rule, while `rg` and `fd`, which the analysis does not know as readers, already run under an allow rule without any `read` check. Such a read is therefore an analysis hold like unrecognized syntax: it asks in `manual`, naming the rule, and `yolo` runs it.

## Out of Scope

- **An OS sandbox.** It would make the guardrails hold for unattended runs ([#133](https://github.com/hakula139/oxide-code/issues/133)).
- **An `auto` mode.** It would decide with a classifier the calls the rules leave open ([#131](https://github.com/hakula139/oxide-code/issues/131)).
