# Tool Permissions and Approval

Every tool call passes through a permission gate. Rules place calls in one of three tiers: deny, ask, or allow. The mode decides the calls the rules leave open, and `plan` also denies every `edit`, `exec`, and `net` call.

Companion docs: [Modals](modals.md), [File Edits](file-edits.md).

## Rule Tables

Rules live in three tables under `[permission]`, one for each tier. Each table holds a pattern list for each permission class:

```toml
[permission.deny]
read = ["~/.aws/**", ".env"]
exec = ["git push --force *"]

[permission.ask]
exec = ["git push *"]
edit = ["Cargo.lock"]

[permission.allow]
exec = ["cargo test *", "cargo build *"]
edit = ["~/notes/**"]
```

The classes are `read` (the `read`, `grep`, `glob`, `tasks`, `bash_output`, and `bash_stop` tools), `edit` (`edit` and `write`), `exec` (`bash`), `net`, and `mcp`. Each tool declares its class in its `ToolSpec`. No built-in tool belongs to the `net` or `mcp` class yet, so those lists parse and validate but match no calls. A `bash` command that accesses the network is still an `exec` call. MCP tools join the `mcp` class with [#178](https://github.com/hakula139/oxide-code/issues/178).

A `Rule` consists of a class and a pattern. Its tier is determined by the list that contains it. Every pattern is compiled when the config loads, so a malformed pattern fails startup and names its file. The pattern `*` matches every call in its class, including calls that name no path, such as `tasks`.

## Modes

`permission.mode` picks one of three modes. `OX_PERMISSION_MODE` overrides it and follows `effort`'s behavior for empty values and typos: an empty value is absent, and a typo fails. `--mode` overrides both for one run, and `/config` credits it to the flag.

- **`manual`**, the default, sends every call the rules leave open to the user, as described in the [approval round-trip](#approval-round-trip). If there is nobody to ask, the run denies them.
- **`plan`** is read-only. It denies every `edit`, `exec`, and `net` call, including a known-safe `bash` read, and reads behave as in `manual`.
- **`yolo`** runs every call that no deny rule or configured ask rule holds. Deny rules hold, shipped ones included, and a configured ask rule still asks, while the shipped ask rules and protected paths do not apply, so `yolo` runs an edit to `.git/hooks` and an `rm -rf` (**Deny rules and the user's ask rules hold in every mode, and `yolo` skips ox's own asks**). A `bash` command holding syntax the analysis does not recognize runs unless a deny rule or configured ask rule matches what the analysis sees (**The analysis recognizes syntax by an allowlist, and an unrecognized command asks in `manual` while `yolo` runs it**). An `exec` deny or ask rule cannot see a binary copied under another name or what a program runs once it starts, so it is a guardrail, and `yolo` runs whatever it misses (**`exec` deny rules are a guardrail**).

Deny rules and configured ask rules apply in every mode, while the shipped ask rules, protected paths, and the analysis's holds apply in every mode except `yolo`. In `plan`, only ask rules for `read` and `mcp` calls still ask, since `plan` denies the other classes first.

The modes correspond to these settings in Claude Code and Codex:

| oxide-code | Claude Code                                                                      | Codex                                                                                   |
| ---------- | -------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `manual`   | `acceptEdits`, which also runs workspace edits                                   | `approval_policy = "untrusted"` with the `workspace-write` sandbox                      |
| `plan`     | `plan`                                                                           | the `read-only` sandbox, which also runs commands that only read                        |
| `yolo`     | `bypassPermissions`, which also asks before an `rm` of a path such as `/` or `~` | `--yolo`, which drops the sandbox and denies what its exec-policy rules would ask about |

### Switching Modes

`Op::SetMode` switches the engine's policy. The TUI sends it from the `/mode` picker, `/mode <mode>`, Tab, or Shift+Tab, while the REPL sends it from `/mode <mode>`. Headless runs send none because `--mode` reaches the engine through `Config` before it starts. The engine confirms each switch with `Event::ModeChanged`, which the TUI records in its session snapshot, the status line shows, and the REPL prints. While idle, the engine applies the switch at once.

During a turn, a compaction, or a sign-in, the op arrives at the operation's `Mailbox`, which keeps it beside the queued prompts and confirms it on receipt. The gate takes a waiting switch before it weighs each call, so a switch applies from the turn's next gated call, including one in the same round. `Engine::serve` applies any switch still waiting once the operation ends, however it ends. Calls already gated keep their decisions, so switching to `plan` does not stop a running command.

Tab and Shift+Tab step through the modes in a fixed cycle (**The keyboard cycle reaches `plan` before `yolo` and wraps at both ends**), and Tab completes the selected command or argument while the command popup is open. The TUI advances from the last mode it requested, so pressing again before the engine confirms the first request moves on to the next mode. The mode enum's declared order, safest first, also controls the picker, argument completion, and the messages that list the modes. The keys are fixed until configurable key bindings land with [#278](https://github.com/hakula139/oxide-code/issues/278).

## Decision Pipeline

Before the gate, the tool's `Tool::prepare` parses the call's input, rejecting a missing or mistyped field, a field the tool does not take, and input `edit` or `tasks` can never run, such as an `edit` whose `old_string` and `new_string` are identical. A rejected call ends with that error as its result, so it neither asks nor reaches the unapproved-call reason below. `grep` and `glob` compile their patterns when they run, so an invalid pattern fails after the gate.

The gate evaluates each call in a fixed order and stops at the first match.

1. **Deny tier** → deny. A deny rule for the call's class matches, or a `bash` command writes a file matched by a deny `edit` rule or reads for certain a file matched by a deny `read` rule: one it redirects into its input, one a wrapper option names, or a reader's literal file argument, including the root of a tree it traverses.
2. **`plan`** → deny an `edit`, `exec`, or `net` call.
3. **Ask tier** → ask. An ask rule for the call's class matches, a `bash` command holds syntax the analysis does not recognize, an edit-class call targets a protected path, or a `bash` command writes a file matched by an ask `edit` rule or marked as protected. A `bash` command also asks if it reads for certain a file matched by an ask `read` rule, if a deny or ask `read` rule matches a file that a reader in it may read without the analysis being certain of it or may match beneath a directory it recursively traverses, if a reader takes a word that expands a variable while any such rule exists, or, while the `rm` default is on, if it runs `rm` with both its recursive and force options. In `yolo`, only a configured ask rule asks here. The shipped ask rules, protected paths, unrecognized syntax, and a reader's possible reads pass this step: a file below a tree it traverses, a word that expands, the input words of `xargs`, the paths of `find`, and a glob whose argument roles or matches remain unknown (**A reader's certain reads face the deny tier, and its possible reads ask outside `yolo`**).
4. **Read-class call** → allow.
5. **Edit-class call inside the workspace** → allow.
6. **Allow tier** → allow. An allow rule or session grant matches the call.
7. **Mode** → allow in `yolo`, and ask in `manual` and `plan`.

A call that would ask is denied as `Decision::Unapproved` in a run nobody attends, which [Stdio Frontends](#stdio-frontends) describes.

An unapproved call's result opens `The {name} call was denied because it needs approval and this run cannot ask for it.`. It then says why the call needs approval, tells the model not to retry it as written, and names the next step, worded as harness output so the model does not read it as the user's instruction. A config change is phrased as a request to the user, since the model should not edit the user config to get past a denial. A call no rule settles opens its reason with `No allow pattern matches it.` and names the pattern to add and the class list under `[permission.allow]` that admits it, quoted as a TOML string from the call's grant. A call with no grant, such as one running more than one simple command or containing a word that expands, asks for a pattern per command, since a broader pattern may still cover it. A call that an ask rule or a built-in rule holds names that rule. For a built-in ask rule, `Policy::config_fix` evaluates the call again with that group off. If the call would then run, the reason also names the `[permission.defaults]` key that turns the group off, and if only an allow pattern would still be missing, it names that key together with the pattern from the call's grant under the group-off policy. Otherwise it suggests no config change. A reader command that may open a file guarded by the `ssh` or `credentials` deny group is held the same way, and its reason names the group without suggesting that the user disable it. An unrecognized command, which only an unattended `manual` run denies, is denied with a reason that names the construct and asks for plain commands joined by `&&`, `||`, `;`, or `|`.

Each step settles the call with a `Verdict`, which pairs the `Decision` with the `Basis` that reached it: a configured rule and its tier, the built-in group behind a shipped pattern or a protected path, a session grant, the read or workspace default, the mode, the first construct of a `bash` command the analysis does not recognize, or for an allowed `bash` command what let each part through. The gate logs every verdict at debug level. A denial names its basis in the result the model reads, such as the `deny.exec` pattern `curl *`, and the approval prompt names the rule that made the call ask. A call the mode asks about has no rule to name, so the prompt shows none.

The tiers apply in this order: deny rules outrank all ask and allow rules, and ask rules outrank all allow rules, session grants, and the workspace allow. Steps 4 and 5 come after the ask tier. Thus, `ask.read = ["~/.aws/**"]` makes reading those files ask, and `ask.edit = ["Cargo.lock"]` makes editing the project's lock file ask.

A `bash` command is allowed at step 6 only if the analysis recognizes all of it, each of its simple commands is allowed by an `exec` rule or is a known-safe read, and every file it writes is inside the workspace or allowed by an `edit` rule. An unrecognized command can still be denied. For example, `deny.exec = ["rm -rf *"]` stops `rm -rf x; echo $((1 + 2))`, but no rule, including `*`, allows it. In `manual`, it asks, and the prompt names the first construct the analysis does not recognize (**The analysis recognizes syntax by an allowlist, and an unrecognized command asks in `manual` while `yolo` runs it**).

## Path Targets

A path tool's target is resolved before any rules run. The tool's `Tool::prepare` method does this in the call's `ToolCtx`, which carries the session's `Workspace`: its cwd and roots. `prepare` expands a leading `~` or `~/` in the path argument to the home directory, as config patterns do. `Access::for_path` then joins the path to the cwd and walks the path one component at a time, as the kernel does. It follows every symlink it encounters, including dangling links, and processes `..` from the current position in the walk. This prevents a `missing/..` detour from hiding a symlink encountered later. Once the first missing component is reached, nothing further exists, so the remaining path is applied as `create_dir_all` builds it. If the walk meets more than 40 symlink hops, a directory it cannot search, or a file that more components follow, the target stays outside the workspace under its joined spelling with no rooted forms. The tool follows native filesystem behavior. A resolved path that is not valid UTF-8 also stays outside the workspace, because rules match it only by its lossy spelling.

An approval names the resolved path, in the title for `edit` and `write` and in the body for `read`, and so do the tool's messages. `read`, `edit`, and `write` open the file at `Access::resolved()`, so a workspace or symlink target whose path holds a non-UTF-8 byte opens as it exists on disk. `grep` and `glob` retain the `path` as written in the call, with only `~` expanded, because read deny rules match it, then walk from the root resolved by `prepare`. `read`, `edit`, and `write` check file size and type both by path and on the opened file whenever they read a file. Their opens refuse a symlink that replaces the resolved final component. On Unix, opens use `O_NOFOLLOW` and `O_NONBLOCK`, preventing a swapped-in FIFO from hanging the open. On Windows, opens use `FILE_FLAG_OPEN_REPARSE_POINT` and fail if the handle is a symlink or junction. Other reparse points need a second open through their filesystem filter, whose handle must reach the same file. On every platform, a symlink swapped into an intermediate directory between the gate and the open is not covered.

Edit and Write recheck the original before publishing and report a concurrent change instead of overwriting it, as [File Edits](file-edits.md) describes.

Each resolved target belongs to one zone:

- **Protected**: Edit-class calls ask at step 3 if the target's resolved path or call-spelled path contains a protected name from an enabled [shipped default](#shipped-defaults). They also ask when the target is in a location where such a name directly inside the cwd or a workspace root resolves. For example, `.vscode -> tools/vscode` protects `tools/vscode` too. Names are compared after dropping default-ignorable code points, applying Unicode compatibility case folding, and trimming trailing dots and spaces. On a case-insensitive file system such as APFS, `.VSCODE` and `.vſcode` open as `.vscode`. HFS+ ignores the zero-width `\u{200c}` in `.g\u{200c}it`, and Windows opens `.git.` as `.git`. On Windows, the existing part of the resolved path is spelled as the file system opens it, with each 8.3 short name written in full and NTFS stream suffixes dropped. Thus, `GIT~1` and `.git::$INDEX_ALLOCATION` count as `.git`.
- **Workspace**: Edit-class calls are allowed at step 5 when the target sits inside a workspace root. The roots are the cwd and each `permission.extra_roots` entry, resolved the same way as a target. The path gate and edit tools read the same set. If the cwd is `/`, `$HOME`, or an ancestor of `$HOME`, the workspace has no roots, including extra roots, so launching there leaves every edit to the allow rules. The check also compares file identity, so aliases kept by resolution, such as macOS's case-insensitive `/users/<name>` or the `/System/Volumes/Data` firmlink, count as the directory they name. An existing regular file with more than one hard link is never a workspace target, because another link can sit outside every root.
- **Outside**: Every other target needs an allow rule, approval, or `yolo`.

`Access::Path` records the protected names a target contains by default group. The policy can therefore apply the groups enabled in the config without resolving the path again.

## Command Targets

A `bash` call's target is its command as parsed by tree-sitter-bash. `Access::for_command` splits the command into simple commands across `;`, `&&`, `||`, `&`, pipes, line breaks, subshells, and compound statements. Each simple command drops the wrappers that lead it, with their options: `builtin`, `command`, `coproc`, `env`, `exec`, `nice`, `nohup`, `stdbuf`, `time`, and `timeout`, which change only how the command runs, and `busybox`, `doas`, `pkexec`, `sudo`, and `xargs`, which change who runs it or which arguments it gets. A `coproc` command is still unrecognized, as the list below explains, so seeing through it serves deny rules alone. For example, `nice -n 5 cargo test 2>&1` runs the simple command `cargo test`, and `sudo -u root rm -rf x` runs `rm -rf x`. Each wrapper's options are parsed by its own grammar, with short options in clusters and values attached or in the next word, as in `sudo -nu root` and `nice -n5`. `xargs` adds a word for the arguments it reads from its input, which expands and so matches any word of a deny or ask rule, or, under `-I`, `-i`, or `--replace`, marks each word holding the placeholder as expanding. Under `-J`, as in BSD `xargs`, only a word that is exactly the placeholder expands, and the input word is added when no word is. Each `-exec`, `-execdir`, `-ok`, or `-okdir` action of `find` adds its command, up to its `;` or a `+` after `{}`, as a further simple command, in which each word holding `{}` expands. A redirection can carry words bash passes to a command: those after a heredoc operator, as in `cat <<EOF notes.txt`, and those after a redirection's target, as in `git >/dev/null push`. tree-sitter-bash parses them as part of the redirection, so the analysis hands them to the simple command bash gives them: the last one of a pipeline or list, the one a `!` negates, or a command of their own after assignments or redirections that stand alone. Where tree-sitter-bash splits one bash word into parts with nothing or only backslash escapes between them, as in `=="x"` or `"x"\ "y"`, the parts form one word. An argument it reads as an anonymous token, such as a bare `==`, still counts as a word, and so does a lone `-` it drops before a redirection, as in `python3 - <<EOF`. Command words are unquoted, a `$'...'` string decodes its escapes as bash does, and a leading unquoted `~` or `~/`, or a leading `$HOME` or `${HOME}` quoted or not, expands to the home directory, as bash expands both from `HOME`. Each output redirection to a file (`>`, `>>`, `>|`, `>&`, `&>`, `&>>`) becomes an edit-class path target, and each input redirection (`<`) a read-class one, both resolved and zoned like a path tool's target. A redirection to `/dev/null`, `/dev/stdout`, `/dev/stderr`, or `/dev/tty` adds no target.

Each simple command retains two word lists. Its program words start at the program that runs, after all assignments and wrappers. Its named words also start at the program unless a leading assignment or an `env` argument sets a variable outside a short list of variables that affect only output, such as `RUST_LOG`, `LANG`, `TZ`, or `NO_COLOR`. Other variables can change which program runs or what it loads, as `PATH`, `LD_PRELOAD`, and `GIT_PAGER` can. In those cases, the named words start at the assignment and include all following words, including wrappers. Thus, `GIT_PAGER=sh git log` needs a rule that names the assignment and is never a known-safe read. A wrapper spelled with a directory, as in `./nice` or `/usr/bin/env`, may be any program, so the named words also start at it, as they do at a wrapper that changes who runs the command or its arguments. Thus, an allow rule for `rm *` covers `nice rm x` but not `sudo rm x`, which needs a rule that names `sudo`. The named words also start at a wrapper whose options the parser does not know or cannot read, as in `env -S`, `nice $LEVEL`, or `sudo -s`, which runs the command through a shell, or that holds a word before its command that bash may expand into several, as an unquoted expansion, a glob, or a brace expansion such as `nice -n {5,rm,-rf,x} true` may, at `xargs` running a wrapper alone, as in `xargs sudo`, and at a `find` with an argument that expands, since each may change what runs. Deny and ask rules still see the program that runs, and after an unknown option they treat each later word as where the program may start, so `sudo --unknown value rm -rf x` still counts as `rm -rf x`.

The analysis recognizes a command by an allowlist over tree-sitter-bash's syntax, and a command holding anything outside it is unrecognized. It recognizes:

- Lists, pipelines, `!`, subshells, `{ ... }` groups, `if`, `case`, `while`, `until`, and `for` over a word list, with their redirections, heredocs, and here-strings.
- Words that are literal, quoted, `$'...'` or `$"..."` strings, brace expansions, or globs, and the expansions that only substitute text: `$name`, `${name}`, and a `${...}` form with a leading `#` for the length, a default, alternate, or error operator, a pattern removal or replacement, or a case change. Each reads a variable, a special parameter, or an array element by number or all of them by `@` or `*`, and a pattern that holds `$` or a backquote is unrecognized, since the grammar leaves it as one token.
- Command and process substitutions, whose commands count as further simple commands.
- A write to a local name, which is an identifier with a lowercase letter that the environment `bash` starts with does not set, or to one of the output variables above. The write may come from a plain or `+=` assignment, a `for` loop, `declare`, `local`, `readonly`, or `typeset` without `-i`, `-n`, or `-x`, `read`, `mapfile`, `getopts`, `printf -v`, `wait -p`, or `unset`, and an `( ... )` array value may key an element only by a number. A quoted value given to `declare` or a builtin like it may not start with `(`, since the builtin parses it again as an array whose keys and values may run commands. `export` names only the output variables.
- `[ ... ]` and `test`, when each token is a word bash passes to `[` and no `-v` or `-R` operand may hold a subscript.
- `eval` with literal arguments, whose joined script is parsed as further simple commands, `source` and `.` with a literal path, `set` turning only `errexit`, `nounset`, `pipefail`, `verbose`, or `xtrace` on or off, and every program and builtin not named below.

A command is unrecognized when:

- It fails to parse, or tree-sitter-bash ends one of its words where bash does not, as at an escaped blank between words or a `$` before a blank, or reads a reserved word as a command name, as it does for `coproc`, which it has no grammar for, and for a compound command after the `time` keyword.
- It has words after a redirection of a compound statement, which bash rejects.
- It evaluates arithmetic: `$((...))`, `((...))`, `let`, a C-style `for`, `[[ ... ]]`, or a `${...}` offset or subscript other than a number. Arithmetic evaluates the value of each variable it reads as an expression in turn, where a subscript runs any substitution, so an indirection or transformation such as `${!n}` or `${x@P}` is unrecognized too.
- It defines a function or runs `select`.
- It writes any other variable, such as `PATH`, `IFS`, `BASH_CMDS`, `GIT_EDITOR`, or an inherited `http_proxy`, at statement level or through a builtin, or assigns as it expands, as `${name:=word}` does. A leading assignment on one command, such as `PATH=/tmp ls`, reaches that command alone, so it moves the named words to the assignment instead.
- Its command name is not a literal word or holds a glob, as in `$CMD -rf x` or `/bin/s? -c ls`.
- It runs `alias`, `bind`, `compgen`, `complete`, `compopt`, `enable`, `fc`, `hash`, `history`, `shopt`, or `trap`, which run code or change what later words run, `eval`, `source`, or `.` with an operand that expands, `jobs -x`, `mapfile -C`, or `set` with any other option.
- A redirection target is not a literal path or contains a glob.
- A `cd`, `pushd`, `popd`, `env -C`, `sudo -D` or `-R`, `pkexec`, or `find -execdir` or `-okdir` runs alongside a redirection or a reader of a relative path, or a program spelled with a relative path such as `./build.sh`, which may then name another file. The analysis still weighs a relative reader operand or redirection target under the working directory and under each directory that a `cd` or `pushd` with one literal target, or a bare `cd`, may have entered, each target joined to the directories before it, so the deny and ask tiers see `cd ~/.ssh && cat id_rsa` as a read of `~/.ssh/id_rsa` in every mode. Keeping every earlier directory covers a change that fails, runs in a subshell, or sits behind `||`. After a change the analysis cannot spell, such as `cd $DIR`, `cd -`, `popd`, or a `cd` in a loop body, a relative reader operand may name any file.
- A directory change may leave the workspace and the command runs anything besides directory changes, as in `cd /tmp/evil && cargo build`, which runs that directory's `build.rs`. Only a first `cd` or `pushd` to one literal directory inside a workspace root, spelled without `..` and run once outside any loop or function body, such as `cd crates/ox-core`, stays inside, while a later directory change or any of the other changers above may leave (**Rules allow nothing that runs after a directory change the gate cannot place**).

A shell such as `sh`, `bash`, or `zsh`, compared by folded name so `BASH` counts too, is a program like any other, and its literal `-c` script is parsed too, so every rule sees the simple commands inside it, as it does those of a literal `eval` script and a substitution. An allow rule must still cover the shell itself, so `sh -c 'npm test'` needs rules for both `npm test` and `sh -c *`, and `curl x | sh` needs one for `sh`.

`su` and `runuser` start a shell, so they count as shells, and their `-c` or `--command` script is parsed the same way. `runuser -u` runs its command without a shell, so that command is parsed as a further simple command.

These wrappers, `find` actions, substitutions, and literal scripts are the only places the analysis looks for a command inside another. Any other program that runs a command from its arguments, its input, or a file, such as `watch`, `fd -x`, `make`, `python3 -c`, or a `git` alias, is the program a rule sees, and variables set by `read` or `printf -v` stay unknown. In `manual`, such a command asks unless an allow rule names the runner. In `yolo`, it runs unless a deny rule or configured ask rule names the runner, since no rule sees the command inside it.

Some read-only commands run without an allow rule. `:`, `echo`, `false`, `printf`, `pwd`, `true`, the `export` and `set` the analysis recognizes, `[`, `test`, `cat`, `head`, `ls`, `tail`, `wc`, `find`, `grep`, and `sed` are safe when every argument is a literal word without globs, the command runs under its bare name, and nothing in the whole command expands a variable. That last condition covers a `case` subject, an assignment, a `for` list, a here-string, and an unquoted heredoc too, since any of them can bring a variable's value into what a safe command prints. The commands that can do more have these guards:

- `[` and `test` count each word other than an option, an operator, or the closing `]` as a file they may read, never one they read for certain, so a string they compare counts as one too.
- `find` must not use an action that runs a command, deletes, or writes a file (`-exec`, `-execdir`, `-ok`, `-okdir`, `-delete`, `-fls`, `-fprint`, `-fprint0`, `-fprintf`).
- `grep` must not use a recursive option or `-d`.
- `sed` must not use `-i`, `-I`, or a script file. Its scripts may only print, delete, substitute, or move text between buffers.

GNU tools accept long options by any valid prefix, so `sed --in` is refused as `--in-place`.

`cat`, `find`, `grep`, `head`, `ls`, `sed`, `tail`, and `wc` are the readers, whether or not a call is safe, and match by their folded bare name, so `/bin/cat` and `CAT` count. Every argument of a reader that may name a file counts as a read of that path. Each reader's option grammar lists the options that take a value, such as `tail -n 20`, `tail -20`, and `grep -A 5`, so those values are not files, while a value that names a file, such as `grep -f patterns.txt`, counts. The leading pattern of `grep` and script of `sed` are not files either unless an option such as `-e` gives one. A long option matches its exact name, or else the one listed option it abbreviates, as getopt accepts, so each grammar also lists an option whose full name abbreviates a listed one, such as `grep --binary` beside `--binary-files`. The gate cannot tell which build runs or how it orders options, so it counts each file any of them would read: some options take a value in one build only, such as `ls -I` in GNU, and getopt stops reading options at the first operand in BSD and wherever `POSIXLY_CORRECT` is set, so `tail log -n 5` may read `-n` and `5` as files. An option missing from a grammar counts its value as a file, which can only make the gate more cautious, and an unlisted long option also counts the leading operand, since it may be the one that gives the pattern. For the same reason, `sed` with an option after an operand is not a safe read, since BSD `sed` may then take that operand as its script. `wc --files0-from` and `find -files0-from` read the files or paths their list names, so they may read any file, while `wc` reads the list itself as an exact file. A pathname pattern also counts as a read of each matching file when the gate runs: `*`, `?`, and `[...]` skip names that start with `.` unless the pattern's name starts with `.` too. The enumerator treats braces as filesystem alternatives, so it does not model bash's lexical brace expansion, which can emit words with no matching filesystem entry. A literal word that every supported argument order and build opens as a file or as the root of a tree it traverses, which excludes a `find` expression's value such as `-name .env`, is a read the analysis is certain of, so the deny and ask tiers weigh it at steps 1 and 3 as they weigh an input redirection, and `deny.read = [".env"]` denies `cat .env` in every mode. If a deny or ask `read` rule matches any other of these reads, the command asks at step 3 outside `yolo`, even when an `exec` rule allows it. An argument that expands a variable may name any file, as may the input words `xargs` or the paths `find` passes to a reader, so it asks whenever a deny or ask `read` rule exists, as the shipped `ssh` and `credentials` rules do. A glob that matches more than 1,024 files or a file whose name is not UTF-8 counts the same way. The `read` rules reach other programs only through input redirections, since a program can open any file once it runs.

A recursive reader keeps tree scope on its directory operands: `grep -r`, `grep -R`, `grep --recursive`, `grep --dereference-recursive`, `grep -d recurse`, `find`, and `ls -R`. Options that name auxiliary files, such as `grep -f`, keep exact scope, and an existing regular file is an exact read even under a recursive option. A recursive call that implicitly searches cwd checks that directory too. A tree is held when its root and a read rule's decoded literal prefix are ancestors of one another, comparing the rule's written and resolved locations through the same directory aliases. This conservatively covers possible descendants without enumerating files, so a tree may be held even when its existing files do not match the rule. Alias comparison covers the roots and prefixes. It does not discover links below a recursive root, so readers that follow child links can reach a separate protected tree ([#658](https://github.com/hakula139/oxide-code/issues/658)).

Reader analysis expands whole-word pathname matches before assigning option roles, so a glob can supply an option or several search roots. A single-match auxiliary-file glob stays exact. Multiple matches keep their ordinary operand roles when all supported argument orders agree and no match can become an option or `find` expression. Otherwise, their ordering may change roles. The analysis retains the written and expanded named paths, keeps possible recursive operands, and marks the remaining reads unknown. Possible value-taking options or `find` expressions also retain cwd as a conservative recursive candidate. A fixed auxiliary value before the ambiguous expansion stays exact, and a file argument before it stays certain, since no match can shift its role. It assumes no locale-specific match ordering. The expansion's matches are never certain. A literal word after it is certain when it is with each glob read as the one word bash sees before expanding it, as a word that expands a variable is, so `cat * ~/.ssh/id_rsa` and `grep key * ~/.ssh/id_rsa` are denied in every mode. A match could still consume that word as the value of a free-text option such as `grep -e` or `ls -I`, or make it the pattern when the matches in `grep`'s pattern slot are all options, so the rule over-denies when the cwd holds such a name, which errs toward the deny as `grep $P .env` does. A recursive reader with no operand, such as `grep -r key` or `ls -R`, searches cwd in every build that reads at all, so cwd is a certain read there.

## Patterns

[Permissions](../guide/permissions.md#rules) gives the user-facing grammar with examples, and this section covers how matching works.

Each class has its own pattern grammar. Allow rules widen what can run without asking, so they match conservatively: a call matches only as it resolves, with names exactly as written in the pattern. Deny and ask rules hold calls back, so they match aggressively across every spelling a call can have. `MatchDiscipline` brings these two approaches together, and the ask tier uses the deny approach.

### Exec Patterns

An allow pattern matches a simple command's named words, including the assignments and wrappers that remain in it. A literal pattern word matches only a command word with that exact value, provided it neither expands nor globs. A `*` before the last word matches one such word, since an expanding or globbing word can become several. A trailing `*` matches all remaining words. Every simple command must match an allow pattern or be a known-safe read for the command to be allowed, so `cargo test *` never covers `cargo test && rm -rf /`.

A deny or ask pattern matches a simple command in any of three spellings: its named words, its program words, or its program words with the program's directory dropped. Its first word matches the command's first word, and each later literal word matches one of the command's later words, in order, with any words between them, so `git push *` holds `git -c a=b push origin` and a `*` adds nothing. Words compare unquoted, with both folded as protected names are. A command word that expands or globs matches any pattern word, since it may become that word when the command runs, so `git push *` also holds `git ${X:-push} origin`. Thus, `rm -rf *` stops `"rm" -rf x`, `/bin/rm -rf x`, `RM -RF x`, `FOO=1 nice rm -rf x`, and `cd src && rm -rf x`.

### Path Patterns

A `read` or `edit` pattern without a leading `/` or `~/` is anchored at each anchor directory, the cwd and each workspace root.

An allow pattern matches the resolved path. If anchored, it matches the path beneath each anchor directory as that directory resolves. Deny and ask patterns also match the path as spelled in the call, after lexical normalization, beneath each anchor directory in both its resolved and spelled forms. This prevents `.env -> ../shared/.env` from routing a read around `deny.read = [".env"]`. They also compare names as protected paths do, so `.env` covers `.ENV` and `.env.`.

Deny and ask patterns compare existing directory identities to recognize equivalent filesystem aliases, retaining the path's remaining components even when they do not exist yet. Protected locations use the same comparison. Each pattern's literal prefix is decoded from globset's grammar and rooted beneath its anchor directories. Matching projects a target's suffix back under that prefix and applies the original compiled glob, so escaped glob characters retain their meaning. The policy keeps the written prefixes and their resolved locations at load time, then checks their current locations too, so `secrets -> ../vault` makes `secrets/**` cover `../vault/key` even when the link appears later. A shell command shares protected roots and directory metadata within its analysis. Direct file checks start fresh. A search walk binds its rule prefixes and anchor directories to the walk's spelling once, then matches entries without further identity queries.

## Shipped Defaults

oxide-code ships named defaults, each a group of rules in one tier, which the [permissions guide](../guide/permissions.md#built-in-rules) lists. A user config turns a group off with `false` under `[permission.defaults]`.

`git`, `direnv`, `editors`, `cargo`, `shell`, `agents`, and `ox` define the protected names of the [Protected zone](#path-targets). `git`, `ssh`, and `cloud` also protect locations in the home directory: the user's git config and credential stores, all of `~/.ssh`, where `authorized_keys`, `authorized_keys2`, `rc`, and `environment` decide what a login runs, and the config directories of the AWS, Azure, Google Cloud, Docker, and Kubernetes CLIs, whose credential helpers and exec plugins run commands. Each covers files that can run or configure code outside the task at hand, so edits to them ask even when an allow rule or the workspace would otherwise permit the edit. The rest of `.claude`, including `worktrees` and `plans`, remains editable. Like any file, a [spill file](truncation.md#spill-files) holding oversized tool output opens for `read` and `grep` at step 4. Editing one asks through `ox`, since spills lie in the data directory. `devices`, `ssh`, and `credentials` add patterns that match like user rules in the same tier. On Unix, `credentials` also denies `/proc/*/environ` and `/proc/*/task/*/environ`, which on Linux hold each process's environment, including any credential `ox` reads from its own, and which `/proc/self` and `/proc/thread-self` paths resolve to. The rest of `/proc`, such as `cpuinfo` or a process's `status`, stays readable, since diagnosing a build or a hung process needs it and it holds no environment. `rm` checks the arguments before `--` of each program a simple command may run, including one a wrapper or `find` action runs, for both a recursive option, `r` or `R` in a short option cluster or a prefix of `--recursive`, and a force option, `f` in a cluster or a prefix of `--force`, so `rm -rfv`, `rm -r --force`, and `rm -f -R` all count. A word that expands, the program name included, counts as either, and GNU `rm` reads options after its operands too, so `rm / -rf` counts. No default joins the allow tier, so an allow rule never overrides one, and `true` in a later layer turns a default back on. A `read` deny default also withholds its files from `grep` and `glob` walks.

## Approval Round-Trip

When the gate asks, the decision travels through the `ops` channel the turn loop polls. `run_tool_round` gates calls one at a time, so at most one approval can be outstanding and no ID fan-out is needed. Consecutive calls whose `ToolSpec` marks them parallel-safe, namely the read-only `read`, `grep`, and `glob` tools, run together once each call passes the gate. This way, an approval never waits on a running call. If a batch is interrupted, results from finished calls are kept and each unfinished call's `ToolCtx` token is cancelled, stopping blocking `grep` and `glob` walks. The TUI places each result under its call. The REPL repeats a call's header above its result when another call's result was printed in between, so batches read the same in live and resumed sessions.

For a call that asks, the dispatcher emits `Event::ApprovalRequested { id, preview, basis, grant }` with the ID, the basis that made the call ask, the session grant described below, and a small `Clone` preview. The preview is an edit diff from `edit::synthesize_chunk`, a diff against the file's current content for `write`, or the command string under the tool name for `bash`, titled `Bash (background)` for a background call. The gate intercepts the call before it runs, just as the parse-error short-circuit returns a synthetic `ToolOutput`. It waits for a decision in `await_approval` through `Mailbox::race_or`, which maps `Op::Interrupt` to `Cancelled` and `Op::Shutdown` to `Shutdown`, and keeps `Op::Queue` and `Op::SetMode` in the turn's `Mailbox`, as every other wait in the turn does. The wait matches `Op::Resolve { id, decision }` and ignores decisions whose IDs do not match the outstanding call, and dropping the wait future is cancel-safe.

Every frontend responds with one of the `ApprovalDecision` variants:

- **`Approve`** runs the call.
- **`AllowForSession`** runs the call and adds a session grant, described below.
- **`Deny`** returns a synthetic error `ToolOutput` stating that the user denied the call. The model receives the refusal as a tool result and can choose another approach.
- **`DenyWithFeedback`** returns the user's text in that error result, attributed to the user, so the model learns why the call was denied and what to do next.
- **`Abort`** ends the turn as `Op::Interrupt` does. The call's result records that it never ran.

In the TUI, an `ApprovalModal` joins the `ModalStack`. The blocked agent must receive a decision whenever the modal is dismissed. However, `ModalStack::handle_key` intercepts Esc and Ctrl+C before delegating, while `clear` drops modals outright. Neither path produces an action of its own, so the stack has a cancel hook, `Modal::on_cancel`, that returns an optional `ModalAction`. On a universal cancel or session-swap `clear`, it resolves a pending approval to `ApprovalDecision::Abort`, matching Esc outside the modal.

`Y` approves, `N` denies, and Esc aborts. `F` opens a one-line feedback editor. Enter denies with the typed text, an empty answer submits nothing, and Esc returns to the choice. Enter does nothing while the choice is shown. Approval and editor submission require a fresh key press, and repeated acceptance keys restart the type-ahead guard. As in every modal, a key held with Ctrl or Alt does nothing outside the editors once the guard expires. Apart from the stack-level Esc / Ctrl+C cancel, the choice ignores every key until 300 ms have passed without one. Each key during that window restarts the timer, preventing a keystroke typed for the prompt underneath or a pasted burst from approving the call. The guard starts when the first body row appears, or the heading for an empty body. Opening an editor invalidates the choice's readiness, and its guard starts when the whole editor appears. An empty or clipped viewport revokes acceptance, and restoring the view restarts the guard.

`A` allows the call and every later call covered by a session grant:

- **Grant:** When the gate asks, `Policy::session_grant` derives the narrowest rule that names the call with `Rule::for_call`. For `bash`, it uses the command's single simple command as its named words, quoting each word when required by the pattern grammar. Thus, `RUST_LOG=debug cargo test 2>&1` offers `cargo test`. For an edit, the grant uses the escaped path, prefixed with `./` inside the cwd or written as an absolute path outside it. The grant travels on `Event::ApprovalRequested` and is offered only if adding its rule would allow the call. Protected paths, ask-rule matches, unrecognized commands, and commands with multiple simple commands offer no grant. Calls with words that expand or glob, and calls containing characters the editor cannot display as themselves, offer no grant either. This ensures the user always sees the exact rule they are granting.
- **Editor:** `A` opens a one-line editor prefilled with the rule's pattern. The user can widen or narrow it, for example to `cargo test *`. Enter checks the edit with `SessionGrant::accept`, which parses the pattern in the call's class and requires it to still cover the call. If it does not, the editor shows the reason inline. Esc returns to the choices through `Modal::captures_esc`, while Ctrl+C still aborts.
- **Engine check:** The accepted rule answers `ApprovalDecision::AllowForSession`. Since a frontend's check is advisory, the gate keeps its own grant for the pending call, admits the answered rule against it with `SessionGrant::admit`, and denies the call with an error if the rule fails.
- **Precedence and lifetime:** An admitted rule joins the engine's policy, where step 6 treats it like a configured allow rule. Deny rules, ask rules, and protected paths still take precedence. The list lives only in the engine's memory and is emptied by `/clear`, `/archive`, and a successful `/resume`. `Event::SessionRulesUpdated` carries it to the frontend, and `/status` lists it under Session Rules by class.

The preview must show everything it approves. Every row wraps. If the body exceeds 16 rows, it scrolls with Up / Down, PageUp / PageDown, and Home / End, and shows a `rows a-b of n` position line. Control and zero-width characters render as `\u{..}` escapes. In a command, every whitespace character after the indentation renders as `·` unless it is a single space. Thus, padding that pushes a chained command off-screen appears as a dotted run.

## Configuration

```toml
[permission]
mode = "manual"
extra_roots = ["~/src/shared"]

[permission.allow]
exec = ["cargo test *"]

[permission.defaults]
rm = false
```

The `[permission]` table parses into a `PermissionTable` on `FileConfig`. `deny_unknown_fields` applies at every level, so an unknown class or default name fails to load and lists the accepted names. Every `permission.<tier>.<class>` list and `permission.extra_roots` entry is concatenated across config layers, while a `permission.defaults` key set in a higher layer replaces the lower one. The merge records the layer behind each appended entry, and `/config` lists every pattern, extra root, and turned-off default with that layer. `Config::load` resolves the policy after the compaction block, including each deny and ask pattern's literal prefix. It also resolves the extra roots with `Workspace::resolve`, failing to load if a root is relative, does not resolve, or is `/`, `$HOME`, or an ancestor of `$HOME`. A root that does not resolve runs through a symlink loop, a directory the walk cannot search, or a file that more components follow, and the error names that component.

A checked-in `.ox/config.toml` is untrusted, so `reject_project_keys` checks it against allowlists: it may set only the `[client]`, `[permission]`, and `[tui]` tables, only request settings in `[client]`, and only `permission.deny` and `permission.ask` in `[permission]`. Any other `[permission]` key there, such as `mode`, `allow`, `extra_roots`, or `defaults`, is rejected with a message pointing to user config. The merge appends project rules to the user's rules, allowing a repo to restrict itself or require approval without widening what the user allowed or turning off a default.

## Stdio Frontends

The `--no-tui` REPL and `-p` headless runs share `render_op`. It passes each `Event::ApprovalRequested` to an `Approver` and sends the decision back as `Op::Resolve`. The request itself never reaches the event sink, so `stream-json` output contains only the call's result.

Whether anyone can answer is a session setting of the engine. `main` calls `Config::set_unattended` for a headless run and for a REPL whose stdin is not a terminal, and the policy then turns every call that would ask into `Decision::Unapproved`, which the gate denies without emitting a request. Such a run passes no `Approver` to `render_op`, and the REPL reads its attendance back from `Engine::attended`.

- **REPL:** When stdin is a terminal, the prompter writes the preview and the rule that made the call ask to stderr, escaping hidden characters, and reads the answer from the next stdin line: `y`, `a` followed by the pattern to allow, `n`, `f` followed by the feedback line, or `x` to abort. An unknown answer, empty feedback, or a pattern the grant does not admit returns to the choices. End of input aborts, and Ctrl+C interrupts the turn, which drops the question. Piped input runs unattended as a headless run does, so a scripted prompt line is never read as an answer.
- **Headless:** When nobody is available to ask, rules and zones decide every call, so a headless run assumes an already-trusted invocation.

The stdio sink escapes control characters other than tabs and line breaks in model and tool text, preventing streamed text or a tool label from redrawing the terminal to disguise the REPL's preview.

## Permission Classes

`Tool::spec` has no default, so every tool declares its class in its `ToolSpec` and a new tool cannot inherit a permissive class. Read-class tools are allowed at step 4, but they still resolve a target, such as the file for `read` or the search root for `grep` and `glob`, so a path-scoped deny or ask rule can match first. Rules target the class, so `deny.read = [".env"]` also stops a `grep` rooted at a `.env` file. Since `grep` and `glob` gate on the search root, they also check every file found during a walk against the `read` deny and ask rules, withholding matches and ending their output with a count of withheld files but no names. A path the walk could not read faces the same check, so the note listing unreadable paths never names a withheld one. A walk cannot ask about each file. A file is checked where it resolves and as spelled in the call beneath the search root, just as the gate checks a read of it. Thus, `.env` is also withheld under a root that is a symlink out of the workspace. Walks do not follow symlinks below the canonical root, so the check needs no I/O.

`edit` and `write` share a class but have different blast radii. `edit` requires an existing file that has been read, so it cannot create files. `write` can create new files and parent directories without a prior Read, while overwriting an existing file still passes through the tracker gate. Both declare `file_path` as their path field, so the resolution and zoning described above apply to them identically.

## Design Decisions

1. **Deny rules and the user's ask rules hold in every mode, and `yolo` skips ox's own asks.** A mode that skipped deny rules would make a deny rule's meaning depend on a setting elsewhere, and a configured ask rule records a call the user wants to see, such as `git push`, whatever the mode. The shipped ask rules, protected paths, and the analysis's holds are ox's defaults for a watched session, and choosing `yolo` opts out of them, so `yolo` runs what they alone hold and changes the fallback from ask to run. A configured ask rule therefore still prompts in a `yolo` session someone attends, and a run nobody attends denies it like any call that would ask. Claude Code's `bypassPermissions` draws the same line: it keeps deny rules, prompts for explicit ask rules, and runs writes to protected paths, while `--permission-prompts none` denies what would prompt in a print run. It also prompts before an `rm` of a critical path such as `/` or `~`, which ox has no rule for. ox's `rm` default holds every forced recursive delete and is a guardrail (**`exec` deny rules are a guardrail**), so `yolo` skips it with the other shipped ask rules. Codex's `approval_policy = "never"` denies what its policy rules would ask about and runs the rest inside its sandbox, which ox lacks, so `yolo`'s guardrails are the rules alone. `plan` denies `edit`, `exec`, and `net` calls ahead of the ask tier because approving one would break the read-only session.
2. **Ask outranks allow.** An ask rule records a call the user wants to see, such as `git push`, even when a broad allow covers it. Placing the ask tier above every allow, including session grants, the workspace allow, and a future classifier, preserves that request as the allows grow.
3. **Protected paths ask.** Editing `.git/hooks`, `.vscode/tasks.json`, or `.envrc` inside the workspace can escalate to code execution outside the task. These paths therefore ask even under `allow.edit = ["*"]`, in every mode but `yolo` (**Deny rules and the user's ask rules hold in every mode, and `yolo` skips ox's own asks**). Asking keeps legitimate edits possible, while a deny would require the user to edit config. A user who never wants to be asked about one group can turn it off.
4. **Words over strings.** Matching `exec` patterns against parsed words gives a rule the same meaning regardless of how the command quotes, spaces, or wraps its words. It also lets an allow pattern reject a word that could expand into several. A lone `*` is the only wildcard, so rules do not depend on how a glob inside a word interacts with shell quoting.
5. **Gitignore-style paths.** Patterns work like `.gitignore` entries, so `.env` and `target` need no `**/` prefix and cover what is beneath them. Anchoring at every anchor directory applies a project rule to each workspace root, while `/` and `~/` keep exact absolute rules available.
6. **Resolve once, act on the result.** Resolving in `prepare` and opening `Access::resolved()` makes the tool open the path the gate checked. A no-follow open makes a symlink swapped into the final component cause the open to fail. A swap in an intermediate directory needs `openat`-style traversal or an OS sandbox ([#133](https://github.com/hakula139/oxide-code/issues/133)).
7. **Project files tighten only.** Honoring a project's `allow`, `mode`, `extra_roots`, or `defaults` would let a teammate's repo broaden what the local user permitted, creating the same privilege-escalation vector as project-set credentials. Appending `deny` and `ask` rules lets a repo restrict itself without that risk.
8. **Deny and ask rules are the enforced boundary for path tools.** The deny and ask lists match both spellings of the path as the file system sees it when the gate checks, each pattern's literal prefix as resolved when the policy loaded, and folded names. It does not cover a symlink swapped into an intermediate directory after the check or files touched by a `bash` command, so an untrusted model still needs an external OS sandbox.
9. **Approval decisions on the op channel.** Routing approvals through `ops` and the `ModalStack` reuses the turn loop's cancel / quit / queue semantics, so approvals need no second channel or control-flow path.
10. **Every decision names its basis.** Carrying the basis with the decision lets the denial, the approval prompt, the headless reason, and the debug log all name the same rule, so the model and the user can see which rule fired, and the user knows which pattern to change.
11. **Mode switches wait for the next gated call.** A switch mid-turn changes how the remaining calls are weighed without revisiting calls that already passed the gate, which would mean cancelling a running command or a pending approval. Confirming on receipt keeps the status line honest about the mode the next call meets.
12. **The keyboard cycle reaches `plan` before `yolo` and wraps at both ends.** Stepping forward visits read-only `plan` before `yolo`, so the first Tab press from the default reaches the safest change. `yolo` stays in the cycle by design, and Shift+Tab steps backward through the same order and wraps from `manual` to `yolo`, so either key can undo an overshoot and both stay symmetric. The footer names the mode Tab selects next, so the most permissive mode is announced before a forward press reaches it. Every mode stays reachable from any start by stepping in either direction, so the shortcuts behave the same whatever the starting config.
13. **Approvals stay in process.** A persisted grant has no disk ground truth to revalidate on resume, unlike a `FileSnapshot` rehash, so restoring it would regress trust. In keeping with the slash-command persistence stance ([**Slash commands never write user config files**](slash-commands.md#design-decisions)), session commands remain reversible, and cross-session writes wait for an explicit confirmed action.
14. **Rules follow command runners, and allow rules see through only the harmless ones.** `yolo` runs whatever no rule holds, so a deny rule that `sudo rm`, `xargs rm`, or `find -exec rm` could step around would guard little there. Deny and ask rules therefore see the command each followed wrapper or `find` action runs, and after an option the parser does not know, every word that may start it. Allow rules see through only the wrappers that change how a command runs, since `sudo` and `xargs` change who runs it and with which arguments, so allowing `rm *` must not allow either. Claude Code strips only `nice`, `nohup`, `stdbuf`, `time`, and `timeout` for its rules and matches `xargs` only without options, relying on asking for the rest, while Codex looks through `sudo` and `env` only for its forced-`rm` check.
15. **The analysis recognizes syntax by an allowlist, and an unrecognized command asks in `manual` while `yolo` runs it.** A list of dangerous constructs misses whatever it forgets, including a construct a grammar update adds, while an allowlist leaves every node kind and builtin nobody judged unrecognized and admits one only when the rules see everything it runs. Substitutions and literal `sh -c` and `eval` scripts qualify, since their commands become further simple commands that every rule weighs. Arithmetic does not, since it evaluates the value of each variable it reads as an expression, and that value is unknown wherever it comes from a file, a substitution, or the environment. Arithmetic over literal numbers alone is harmless but rarely written, since a script computes with variables, so it stays unrecognized as well. tree-sitter-bash's error recovery can fold one command's words into another's or into a redirection, so the words rules see may not be the words bash runs, and an allow rule could cover a command it does not name. The grammar can also end a word where bash does not without a parse error, as at an escaped blank between words, a line continuation that bash removes to join two tokens, or a `$` it reads together with the blank after it. Such a command is unrecognized too: outside quotes, the analysis accepts only blanks and line continuations between tokens, backslash escapes alone only between the parts of one command word, line continuations alone only after a control operator, and no blank inside a `$` expansion. So is a command whose name, or whose first word after the `time` keyword and its options, is a reserved word, which happens only where the grammar has no rule for the construct. Asking keeps a misparse or a construct nobody judged from reaching an allow rule, at the cost of an occasional prompt for valid syntax, which rewriting the command avoids, and the prompt names the construct so the rewrite is clear. `yolo` skips the analysis's holds, so it runs such a command unless a deny rule or configured ask rule matches what the analysis did see. Denying it there would add nothing a deny rule can promise, since `exec` deny rules are a guardrail (**`exec` deny rules are a guardrail**), and would block valid syntax with no setting to allow it. Claude Code's tree-sitter analysis also walks an explicit allowlist of node kinds and asks for anything outside it, but treats every `eval`, `source`, and `.` as a construct it cannot analyze, while ox parses a literal `eval` script and lets a rule name a sourced file, as in `source .venv/bin/activate`, since naming the file vouches for what it runs. Its bypass mode overrides that ask, and Codex splits a command only when it is plain words joined by `&&`, `||`, `;`, and `|`, matching anything else as one command, so the bypass modes of both run an unrecognized command.
16. **Attendance is an engine setting.** The policy knows whether anyone can answer and settles a call that would ask as `Unapproved`, so the engine denies it without a request and words the denial itself. A frontend reply would make every frontend without a person behind it reimplement that answer, and a request no one answers would stall the turn. Codex's `approval_policy = "never"` and Claude Code's `--permission-prompts none` likewise live in the core session config.
17. **A command may write only a local name or an output variable.** A variable bash reads, such as `PATH`, `IFS`, or an entry in `BASH_CMDS`, changes what later words run without changing the words, and an exported or inherited one such as `GIT_EDITOR` or `http_proxy` changes what a later program does. The variables bash and every program read have no complete list, so the analysis admits a write only to a name nothing outside the command reads: one with a lowercase letter, which none of the variables a noninteractive bash reads has, that the environment `bash` starts with does not set, so the write exports nothing. `declare`, `local`, and `typeset` with `-i`, `-n`, or `-x` are unrecognized, since an integer variable evaluates each later value as arithmetic, a name reference sends later writes to the variable its value names, and `-x` exports, while `export` admits only the output variables, which every program the command runs may read without harm. A leading assignment on one command reaches that command alone, so a rule that names the assignment can allow it, as in `PATH=/opt/bin make`. Claude Code's tree-sitter analysis likewise refuses `declare -i` and `-n` for the arithmetic and name-reference reasons, and it refuses `-a` and `-A` as well. ox admits those two, since it leaves an array key other than a number unrecognized and refuses a quoted value that starts with `(`, which the builtin would parse again as an array the grammar never shows.
18. **Rules allow nothing that runs after a directory change the gate cannot place.** A program reads the directory it runs in, so `cd /tmp/evil && cargo build` runs that directory's `build.rs` under rules that name both parts. The gate places only a first `cd` or `pushd` with one literal target, since a later relative target starts wherever the first one led, and a `cd` in a loop or function body may run more than once. It refuses a `..`, which bash's `cd` applies to the spelled path while the gate resolves symlinks first, so `cd link/../x` can land elsewhere. `env -C`, `sudo -D`, `pkexec` (which runs in `/`), and `find -execdir` count as leaving without resolving their targets, which costs little because agents rarely use them. A lone directory change stays allowed, since it runs nothing there and each `bash` call starts a fresh shell. A relative program path still asks after any directory change, even inside the workspace, since it then names a different file from the one the rule meant. Claude Code likewise checks a compound command's `cd` target as a path and asks when it leaves the project.
19. **`exec` deny rules are a guardrail.** An `exec` deny or ask rule, and a `read` or `edit` rule or protected path applied to a `bash` command, see every simple command and redirection the analysis finds, through the followed wrappers, `find` actions, and literal scripts, but no analysis of a command line can make them a boundary. A rule that names a program cannot match a copy or link of it under another name, as in `cp /bin/rm ./x && ./x -rf ~`, and no rule sees what a program runs or writes once it starts, such as `python3 -c`, `tee`, a `build.rs` that `cargo build` runs, a `Makefile`, or a git alias, while `yolo` also runs the edit that writes such a script. Claiming a boundary would make each of these routes a vulnerability, and the list has no end. Two properties do hold, and a gap in either is a vulnerability. A `bash` command runs without asking in `manual` only when step 6 allows it, as the [decision pipeline](#decision-pipeline) describes, and path deny and ask rules stay a boundary for the path tools in every mode where they apply (**Deny and ask rules are the enforced boundary for path tools**). Claude Code's bypass mode keeps deny rules but overrides its parse-failure ask, and Codex's `--yolo` keeps its exec-policy rules without a sandbox, so neither offers more.

20. **A reader's certain reads face the deny tier, and its possible reads ask outside `yolo`.** A deny rule's meaning should not depend on the mode (**Deny rules and the user's ask rules hold in every mode, and `yolo` skips ox's own asks**), so `cat ~/.ssh/id_rsa` is denied in `manual` as `cat < ~/.ssh/id_rsa` is, where a prompt would offer to approve a read the `read` tool denies. A rule that matches a directory covers everything below it, so the root of a tree a reader traverses is a certain read, and `grep -r key ~/.ssh` is denied as `cat ~/.ssh/id_rsa` is. A file below that root, a word that expands, and a glob whose roles stay unknown only may reach a held file, and a rule with a broad prefix such as `/**/.env` may match below every directory, so treating them as certain would deny `find .`, `grep -r TODO src`, and `ls -R` under that rule. A guardrail that denies safe reads teaches users to drop the rule, while `rg` and `fd`, which the analysis does not know as readers, already run under an allow rule without any `read` check. Such a read is therefore an analysis hold like unrecognized syntax: it asks in `manual`, naming the rule, and `yolo` runs it.

## Out of Scope

- **An OS sandbox.** It would make the guardrails hold for unattended runs ([#133](https://github.com/hakula139/oxide-code/issues/133)).
- **An `auto` mode.** It would decide with a classifier the calls the rules leave open ([#131](https://github.com/hakula139/oxide-code/issues/131)).
