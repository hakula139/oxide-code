# Cancellation and Queued Input

How the TUI cancels work on Esc or Ctrl+C, exits on a second Ctrl+C from idle, and queues the prompts typed while a turn runs. [Engine](engine.md) covers the operation and event contract these controls drive.

## Controls

The TUI exposes these controls and behaviors:

- **Cancel and exit.** Esc / Ctrl+C cancels active work. Dual-press Ctrl+C exits from idle, and dual-press Ctrl+D exits from idle with an empty input buffer, since Ctrl+D deletes forward while there is text. `/exit` quits from any state, and a turn in flight ends as a shutdown does.
- **Queue input.** Enter while busy appends to the app's `PromptQueue`, rendered as a dim preview above the input, and forwards the prompt as `Op::Queue`.
- **Drain input.** The engine splices each forwarded prompt in at its next round boundary, as [Turn Pipeline](engine.md#turn-pipeline) describes, and confirms it with `Event::PromptDrained`. A turn that ends first drops the prompts it still holds, and once it completes or fails the TUI submits the queue head as the next turn. A prompt whose automatic compaction failed was never sent, so the TUI hands it back (**The TUI owns the queue**). A failed compaction partway through a turn ends the turn and leaves the queue waiting, as [Inside a Turn](compaction.md#inside-a-turn) describes. A refused turn that the engine rolled back (`TurnRolledBack`) hands back its prompt and the queued prompts it took in the same way, or after a mid-turn compaction only the queued prompts it took in since.
- **Interrupt work.** Cancellation drops the `agent_turn` future: reqwest closes the SSE stream, the bash tool kills the command's process tree, and a dim italic `(interrupted)` marker lands in chat. The transcript then ends on a `[Request interrupted by user]` user message, so the model knows the user abandoned that prompt.
- **Show status.** The status bar puts the key that stops the work beside the spinner: `Streaming · Esc to interrupt`, `Running {tool} · Esc to interrupt`, `Compacting · Esc to interrupt`, `Signing in · Esc to cancel`, `Signing out`, `Clearing`, `Resuming`, `Archiving`, `Searching`, `Deleting`, `Renaming`, `Updating model`, and `Cancelling`. An armed exit names the keys that confirm it: `Press Ctrl+C or Ctrl+D again to exit` with an empty input, and `Press Ctrl+C again to exit` while the input holds a draft, where Ctrl+D deletes forward.

The bare REPL maps SIGINT the way a shell does when stdin is a terminal. During an operation, it sends `Op::Interrupt`, and once cancellation ends the operation, `render_op` drops any approval question still awaiting an answer. At the prompt, SIGINT discards the line and prompts again, so only the end of input exits. With piped stdin, SIGINT ends the run, as SIGTERM and SIGHUP always do.

## Design Decisions

The picks lean toward the Codex precedent on most surfaces, since it is the one Rust reference and its patterns map onto our async / actor architecture without reshaping. The wire-shape choice (**Mid-turn drain at round boundary, raw consecutive User messages on the wire**) is the deliberate exception.

1. **Drop-the-future cancellation.** Esc / Ctrl+C drops the `agent_turn` future from the agent loop, which is simpler than Codex's protocol message. The `Tool::run` contract requires each tool to stop its work when the future drops, to stop on the call's `ToolCtx` cancel token, which the dispatcher cancels after the drop, or to finish the work together with its bookkeeping. The `grep` and `glob` walks run on a blocking thread the drop cannot stop, so they check the token. reqwest closes the SSE stream on drop, and the bash tool's `ShellTree` kills the whole process tree, so descendants that a command started with a trailing `&` stop with the shell. Edit and Write run each file write and its tracker record in one spawned task, so a write that lands after the cancel is still recorded.

2. **Commit only settled state on cancel.** A cancel mid-stream discards the partial assistant message, as Codex does. The TUI keeps the streamed prefix with an `(interrupted)` suffix. A cancel during a tool round commits the assistant message with a result for every call, because the finished calls already changed the workspace and the model must see them. Each unfinished call gets an `is_error` result saying the user interrupted it, so the transcript never holds an orphan `tool_use`. The result for a call stopped mid-run says it may have run partially, and the one for a call that never started, including one awaiting approval, says it did not run.

   The turn then ends on a `[Request interrupted by user]` user message after whatever it committed, and a shutdown mid-turn ends the same way. Without the marker, the cancelled prompt and the next one reach the model as two unanswered prompts, and it answers both. Claude Code records the same text for a cancel mid-stream and a `for tool use` variant after a tool round. oxide-code uses one text for both, since the round's results already mark each interrupted call. The prompt itself stays in the transcript, since a tool round may already have acted on it and the chat still shows it. The marker is an ordinary message, so the session file and `--continue` replay it unchanged, and a resumed chat shows it as the `(interrupted)` line.

3. **Mid-turn drain at round boundary, raw consecutive User messages on the wire.** Each queued prompt becomes its own `User` message with one `Text` block. Anthropic accepts consecutive same-role messages. oxide-code deliberately drops the `<system-reminder>` envelope that Claude Code and opencode wrap with, which keeps persistence trivial.

4. **The TUI owns the queue.** `PromptQueue` holds the active prompt and the prompts queued behind it, each kept as its line, typed or the `/init <file>` a picker choice stands for, and the text the engine receives, which differ for a `//` escape and for the prompt a slash command such as `/init` builds. A failed turn hands a slash prompt back to an empty input as its line, with a note that Enter runs the command again against the current files, but back to the queue as the prompt it built, so draining the queue never opens a picker or re-resolves a command mid-run. A queued prompt leaves it only when a matching `PromptDrained` arrives, when it starts a turn of its own, when Esc recalls it into the input, or when a session switch discards it (**A cancel leaves the queue to the user**). A prompt the engine reports unsent goes back to the input, or to the head of the queue when other prompts wait or the input holds a draft, and the queue then waits for the user. The queue counts the leading entries the in-flight turn holds, and a drain pops the head only when it names that head. The TUI forwards queued prompts only while a turn runs that neither a pending cancel nor an automatic compaction holds, since either may end the turn before a round boundary takes them. During any other operation it holds new submits, which start as a turn of their own when the operation ends ([**One operation in flight, ended by its terminal event**](#design-decisions)). The idle engine discards a late `Op::Queue`, since the TUI submits it again.

5. **A cancel leaves the queue to the user.** After a cancel the TUI goes idle without submitting the queue head, even when the turn completed before the cancel landed, and the queue stays held until the next submit, whatever other operation ends meanwhile. A cancel that lands before the engine records the prompt marks it unsent, so the TUI hands it back the way a failed automatic compaction does, with no interrupted marker in chat. Esc on idle pops the most recent queued prompt into the textarea for editing, gated on the buffer being empty so a draft is never silently overwritten. The next submit joins the back of the queue and starts a turn with its head, so prompts keep the order they were typed in. A slash command that builds a prompt, such as `/init`, is the exception: its line is already in the chat, so it starts its own turn, and the queued prompts splice in behind it. A session switch discards queued prompts with a notice naming the count, since they were typed for the conversation that just ended. `/clear`, bare `/archive`, and `/resume` discard only the prompts queued before them and hold the input busy until the new session is ready, so a prompt typed meanwhile waits in the queue and runs in the new session. A failed switch holds that prompt, and a retry that lands still runs it, while a submit before the retry means the user went on in the current session, so the retry discards it too. Esc during a switch cannot stop it, but leaves the waiting prompts to the user as after any cancel. `/compact` keeps the queue, because the conversation goes on from its summary.

6. **One operation in flight, ended by its terminal event.** `App::in_flight` holds the idle-only op the engine runs, from its dispatch to the terminal event `TurnEnd::of` matches for it, the contract the stdio driver ends each op through ([**One terminal event per operation**](engine.md#design-decisions)). The App is busy exactly while an op is in flight, so it never sends an idle-only op, `/rename` and `/model` included, before the previous op's terminal event. `App::end_operation` alone decides what follows an op. A cancel holds the queue, and so does a failure that `PromptQueue::fail_turn` settles by handing back an unsent or rolled-back prompt or by holding the queue after a failed compaction or session switch. A held queue waits for the user's next submit, so a later operation's end never starts prompts typed for a transcript or session the user did not get. Otherwise the queue head starts. An op that ran no turn defers the head while a modal that may send an idle-only op stays open, as the `/resume` picker does after an archive toggle and the `/delete` confirm after its lookup, since a started prompt would make that op fail as busy. `Modal::sends_idle_only_ops` names those modals, so the rule holds whatever opened the modal, and the head starts once the user closes the last of them. A read-only modal, such as `/help`, defers nothing. No modal that sends idle-only ops can be open when a turn ends, since the `Mutating` commands that open one are refused while busy. The status bar's label derives from the in-flight op and the latest stream, tool, or automatic compaction event, and a pending cancel keeps `Cancelling` until the terminal event. An armed exit is a separate deadline, `App::exit_armed`, which only an idle input arms and the next op clears. The App itself routes Esc, Ctrl+C, and Ctrl+D, whose meaning depends on the run state, and tells the input only whether to draw its busy rules, so no decision reads state back from a view.

7. **Cancellation rides the existing `Event` channel.** `Event::Cancelled` covers both the TUI and `StdioSink`. No new event channel.
