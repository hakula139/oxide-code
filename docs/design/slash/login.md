# Login and Logout

`/login` signs oxide-code in to a Claude account using credentials it owns. `/logout` removes those credentials.

## Implementation

`/login` forwards `Op::Login`. The engine starts a loopback listener on an available port and emits `Event::LoginStarted` with the authorization URL. The TUI opens that URL in a browser and prints it in case the browser does not open. When the browser returns to `http://localhost:<port>/callback` with the matching `state`, the engine exchanges the code and verifier for tokens, writes them to `$XDG_DATA_HOME/ox/credentials.json`, and emits `Event::SignedIn` with the source that requests will use.

`/logout` forwards `Op::Logout`. The engine deletes that file and, if the session was using it or is signed out, loads the Claude Code login in its place. `Event::SignedOut` reports whether a login was removed, which source requests will use afterward, and why a stored Claude Code login could not take over. Both commands end with a message naming that source using the label shown by `/status`.

Credentials resolve in this order: `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_API_KEY`, `client.api_key`, `CLAUDE_CODE_OAUTH_TOKEN`, the oxide-code login, then the Claude Code login. Both stored logins use the same refresh path, with a separate file and lock for each. The Claude Code login's lock is the directory Claude Code's `proper-lockfile` creates beside the real path of its config directory, as in `~/.claude.lock`, and both tools hold it the same way: the holder refreshes its mtime every 5 seconds, a lock left untouched for 10 seconds counts as abandoned, and a holder whose lock another process took over in the meantime, as after it was suspended, stops refreshing it and leaves it in place. A waiter whose token has expired once the 20-second wait ends fails with a transient error that names the lock. A request retries it with backoff, so the user is not told to sign in again, and a session it signs out loads the login again on its next prompt.

A session loads its stored login at startup or sign-in, keeping the access token and its expiry in memory. A request made within 5 minutes of that expiry first reloads the login from its store, which refreshes the token and writes it back unless another process has already done so. Because every copy of the client shares the token, concurrent requests, such as the title request during a turn, wait for a single refresh.

When the API rejects a stored login with HTTP 401, the session reloads it and resends the request once, using the token another process stored or, if the store still holds the rejected token, one refreshed regardless of its expiry. If that refresh fails or no refresh token is stored, nothing is resent, and the error names the login's sign-in step, as it does when the resent request also gets a 401. Env vars and `client.api_key` are never reloaded, and their 401 fails at once.

Either reload runs on a task of its own, which keeps the token locked until the reload finishes. A request cancelled mid-refresh, such as a turn interrupted with Esc or a title request that `/rename` stops, therefore still leaves the rotated tokens in the store and in the session. Since the refresh invalidates the old refresh token, losing them would force a new sign-in. Shutting down would still cancel the task, so exiting waits for every reload in flight, including one for a login that `/login` replaced. A reload spends at most the 20-second wait for another process's lock and the 15-second token request, plus any Keychain prompt it raises.

Writing the rotated tokens back can fail, as when the Keychain refuses the write or the credentials file cannot be replaced. The session then logs a warning and keeps the rotated refresh token with the access token. While the store still holds the refresh token the session replaced, each reload uses the session's tokens in place of the stored ones and writes the next refresh's tokens back, warning again if that write fails, so the store catches up once writing succeeds. Any other refresh token in the store was written by another process, such as `claude` or a second `ox`, so the session adopts the stored login. Until the store catches up, another process that refreshes the login sends the invalidated refresh token, so its refresh fails.

A refresh required by a request, whether for an expired token or after a 401, retries the request with backoff when the token endpoint sends no response or a server error, as a transient API failure does. Any other refresh failure ends the request with the sign-in step.

## Design Decisions

1. **oxide-code keeps its own credential store.** Claude Code stores its login in the macOS Keychain item `Claude Code-credentials` or in `.credentials.json` in its config directory, and its `/logout` deletes that store. The directory is `~/.claude` unless `CLAUDE_CONFIG_DIR` moves it, in which case the Keychain item name gains `-` and the first 8 hex digits of the SHA-256 of the variable's value, and oxide-code reads the same variable to find the same store. oxide-code stores its login only in its own file, which `/logout` deletes, so signing out of one tool leaves the other signed in. Refreshing a Claude Code login still writes the rotated tokens back to Claude Code's store because the refresh invalidates the old refresh token.

2. **One file on every platform, in Claude Code's JSON shape.** Codex and pi both store their logins in an `auth.json` file with mode `0600`, which requires neither a Keychain prompt nor platform-specific code. The file contains the same `claudeAiOauth` document as Claude Code's credentials file, so one parser, refresh path, and write-back process serve both stores. It is written atomically with mode `0600` in a `0700` directory, like the `user-id` file beside it. The token is stored in plaintext at rest, as it is in Claude Code's file store.

3. **The oxide-code login takes precedence over the Claude Code login.** Signing in with `/login` is a choice made in oxide-code, so that login takes precedence over one inherited from Claude Code. If an oxide-code login exists but fails, for example because it expired without a refresh token, the search ends with its own recovery step. A broken login therefore never quietly yields to the Claude Code account. Env vars and `client.api_key` still take precedence over both stored logins, and `/login` explains when one of them keeps the session on another credential. Like the Claude Code login, the oxide-code login is sent only to first-party base URLs.

4. **The flow matches Claude Code's login.** It uses Claude Code's client ID, the Claude.ai authorize URL `https://claude.ai/oauth/authorize` that Claude Code's `claude.com/cai` URL redirects to, the token URL `https://platform.claude.com/v1/oauth/token`, and the scopes Claude Code requests at sign-in. As a result, the tokens refresh and authorize like a Claude Code login. The verifier and `state` are 32 bytes from the OS random source, base64url-encoded, and the challenge is the base64url SHA-256 of the verifier (`S256`). The redirect URI names `localhost`, as Claude Code's does, and the listener binds `127.0.0.1` behind it, as pi's does. It reads connections concurrently, so an idle connection opened by the browser ahead of time never holds up the redirect. It answers only `GET /callback` and redirects the browser to Claude's success page. A callback without the sign-in's `state` gets a 400 while the listener keeps waiting, so a stray local request cannot end the sign-in.

5. **The engine runs the flow, and the TUI opens the browser.** The engine owns the API client, so it can swap the credential in place without passing a token between the engine and frontend over the protocol. Each request adds the credential header itself, so the swap cannot fail and keeps the connection pool. The frontend handles opening the browser because it knows whether one can appear. `Op::Interrupt` closes the listener, and login fails if the browser does not return within 5 minutes. Prompts typed during sign-in wait in the TUI and run once sign-in succeeds or fails. Cancelling with Esc ends the sign-in like a cancelled turn, marking it interrupted and keeping those prompts queued.

6. **Signed out is a session state.** If no explicit credential is set and no stored login works, an interactive session starts signed out and explains why, allowing `/login` to sign it in. Prompts fail with a pointer to `/login` until a credential resolves. When a transient failure signed the session out, such as a held refresh lock or a token endpoint that sent no response, at startup or as the Claude Code login took over after `/logout`, each prompt and `/compact` first loads the stored login again, emitting `Event::LoginRestored` when it succeeds, until the failure turns permanent. The load runs on a reload task, so Esc ends the wait while a refresh still writes back. If `/logout` leaves no credential, the session stays open in the same state. `-p` and `--no-tui` sessions still fail at startup because they cannot run `/login`.

7. **TUI only.** `-p` runs no slash commands, and the `--no-tui` REPL runs only the typed session and model commands. To sign in for those modes, run `ox` once and use `/login`, or set `CLAUDE_CODE_OAUTH_TOKEN`.

8. **Requests read the store only near expiry or after a 401.** Claude Code refreshes its login whenever a request falls within 5 minutes of expiry, so a long session never sees the token expire. Because reading the macOS Keychain on every request is slow and can prompt, oxide-code does the same using the expiry it holds in memory.

9. **A 401 refreshes the login whatever its expiry.** Because the API can reject a token that the local clock still counts as valid, for example when the two clocks disagree, counting a rejected token as expired lets the session recover without a new sign-in while the refresh token still works.

10. **The stored refresh token shows whether another process wrote the store.** A refresh invalidates the refresh token it sends, so a store still holding the one the session replaced has seen no sign-in or refresh since, and any other refresh token came from a newer one. Claude Code also rewrites the document to save MCP server logins under `mcpOAuth`, so comparing the whole document would drop the session's tokens after a write that left the login untouched.

## Out of Scope

- **Signing in from another machine.** The redirect returns to the loopback listener, so a browser on another device, as over SSH, cannot finish the sign-in. Claude Code and pi let the user paste the code back into the terminal for this case, which [#239](https://github.com/hakula139/oxide-code/issues/239) tracks.

## Sources

- `crates/ox-core/src/client/anthropic.rs`: `Client::set_auth`, which swaps the credential that each request sends, and `Client::finish_reloads`, which waits for the reloads in flight.
- `crates/ox-core/src/client/anthropic/transport.rs`: `MessagesRequest`, which carries the credential into every attempt, and `post_messages`, which resends a request after a 401.
- `crates/ox-core/src/config.rs`: `Config::load`, which starts an interactive session signed out.
- `crates/ox-core/src/config/auth.rs`: `AuthSource`, resolution order, the stored-login search, and `Auth::credential`, which refreshes a stored login before a request.
- `crates/ox-core/src/config/login.rs`: PKCE, the loopback listener, and code exchange.
- `crates/ox-core/src/config/oauth.rs`: credential stores, refresh, write-back, and `SessionLogin`, the token a session holds.
- `crates/ox-core/src/engine.rs`: `Engine::ensure_signed_in`, which retries a stored login after a transient sign-out, `Engine::login` and `Engine::logout`, which swap the client's credential, and `Engine::finalize`, which waits at exit for the reloads in flight.
- `crates/ox-core/src/protocol.rs`: `Op::Login`, `Op::Logout`, `Event::LoginStarted`, `Event::SignedIn`, `Event::LoginRestored`, and `Event::SignedOut`.
- `crates/ox-core/src/util/path.rs`: `claude_config_var` and `claude_dir`, which follow `CLAUDE_CONFIG_DIR` to Claude Code's config directory.
- `crates/ox-tui/src/app/events.rs`: browser launch and sign-in messages.
- `crates/ox-tui/src/components/status.rs`: `Status::SigningIn`, the status line while the browser is out, and `Status::SigningOut`.
- `crates/ox-tui/src/slash/login.rs`: `LoginCmd` and `LogoutCmd`.
