# Cancellation and Queued Input

How the TUI cancels work on Esc or Ctrl+C, exits on a second Ctrl+C from idle, and queues the prompts typed while a turn runs.

## Implementation

The TUI exposes these controls and behaviors:

- **Cancel and exit.** Esc / Ctrl+C cancels active work. Dual-press Ctrl+C exits from idle, and Ctrl+D exits when idle with an empty input buffer. `/exit` quits from any state, and a turn in flight ends as a shutdown does.
- **Queue input.** Enter while busy appends to the app's `PromptQueue`, rendered as a dim preview above the input, and forwards the prompt as `Op::Queue`.
- **Drain input.** `agent_turn` splices each forwarded prompt into `messages` as a trailing User message at its next round boundary and confirms it with `Event::PromptDrained`, so the model sees new instructions in the next API request without aborting in-flight work. A turn that ends first drops the prompts it still holds, and once it completes or fails the TUI submits the queue head as the next turn. A prompt whose automatic compaction failed was never sent, so the TUI hands it back to the user and leaves the queue waiting. A failed compaction partway through a turn ends the turn and leaves the queue waiting too, as [Inside a Turn](../agent/auto-compaction.md#inside-a-turn) describes. A refused turn that the engine rolled back (`TurnRolledBack`) hands back its prompt and the queued prompts it took in the same way, or after a mid-turn compaction only the queued prompts it took in since.
- **Interrupt work.** Cancellation drops the `agent_turn` future: reqwest closes the SSE stream, the bash tool kills the command's process tree, and a dim italic `(interrupted)` marker lands in chat. The transcript then ends on a `[Request interrupted by user]` user message, so the model knows the user abandoned that prompt.
- **Show status.** The status bar puts the key that stops the work beside the spinner: `Streaming · Esc to interrupt`, `Running {tool} · Esc to interrupt`, `Compacting · Esc to interrupt`, `Signing in · Esc to cancel`, `Signing out`, `Clearing`, `Resuming`, `Archiving`, and `Cancelling`. An armed exit shows `Press Ctrl+C again to exit`.

The bare REPL maps SIGINT the way a shell does when stdin is a terminal. During an operation, it sends `Op::Interrupt`, and once cancellation ends the operation, `render_op` drops any approval question still awaiting an answer. At the prompt, SIGINT discards the line and prompts again, so only the end of input exits. With piped stdin, SIGINT ends the run, as SIGTERM and SIGHUP always do.

## Design Decisions

The picks lean toward the Codex precedent on most surfaces, since it is the one Rust reference and its patterns map onto our async / actor architecture without reshaping. The wire-shape choice (3) is the deliberate exception.

1. **Drop-the-future cancellation.** Esc / Ctrl+C drops the `agent_turn` future from the agent loop, which is simpler than Codex's protocol message. The `Tool::run` contract requires each tool to stop its work when the future drops, to stop on the call's `ToolCtx` cancel token, which the dispatcher cancels after the drop, or to finish the work together with its bookkeeping. The `grep` and `glob` walks run on a blocking thread the drop cannot stop, so they check the token. reqwest closes the SSE stream on drop, and the bash tool's `ShellTree` kills the whole process tree, so descendants that a command started with a trailing `&` stop with the shell. Edit and Write run each file write and its tracker record in one spawned task, so a write that lands after the cancel is still recorded.

2. **Commit only settled state on cancel.** A cancel mid-stream discards the partial assistant message, as Codex does. The TUI keeps the streamed prefix with an `(interrupted)` suffix. A cancel during a tool round commits the assistant message with a result for every call, because the finished calls already changed the workspace and the model must see them. Each unfinished call gets an `is_error` result saying the user interrupted it, so the transcript never holds an orphan `tool_use`. The result for a call stopped mid-run says it may have run partially, and the one for a call that never started, including one awaiting approval, says it did not run.

   The turn then ends on a `[Request interrupted by user]` user message after whatever it committed, and a shutdown mid-turn ends the same way. Without the marker, the cancelled prompt and the next one reach the model as two unanswered prompts, and it answers both. Claude Code records the same text for a cancel mid-stream and a `for tool use` variant after a tool round. oxide-code uses one text for both, since the round's results already mark each interrupted call. The prompt itself stays in the transcript, since a tool round may already have acted on it and the chat still shows it. The marker is an ordinary message, so the session file and `--continue` replay it unchanged, and a resumed chat shows it as the `(interrupted)` line.

3. **Mid-turn drain at round boundary, raw consecutive User messages on the wire.** Each queued prompt becomes its own `User` message with one `Text` block. Anthropic accepts consecutive same-role messages. oxide-code deliberately drops the `<system-reminder>` envelope that Claude Code and opencode wrap with, which keeps persistence trivial.

4. **The TUI owns the queue.** `PromptQueue` holds the active prompt and the prompts queued behind it, each kept as the line typed and the text the engine receives, which differ for a `//` escape and for the prompt a slash command such as `/init` builds. A failed turn hands a slash prompt back to an empty input as its line, so Enter runs the command again against the current files, but back to the queue as the prompt it built, so draining the queue never opens a picker or re-resolves a command mid-run. A queued prompt leaves it only when a matching `PromptDrained` arrives, when it starts a turn of its own, when Esc recalls it into the input, or when a session switch discards it (decision 5). The queue counts the leading entries the in-flight turn holds, and a drain pops the head only when it names that head. While `Status::Compacting`, `Status::SigningIn`, `Status::SigningOut`, `Status::Clearing`, `Status::Resuming`, `Status::Archiving`, or `Status::Cancelling`, no turn may be left to splice prompts in, so the TUI holds new submits and forwards them in order once a turn resumes streaming. A compaction partway through a turn is no exception, since its failure ends the turn. The idle engine discards a late `Op::Queue`, since the TUI submits it again.

5. **A cancel leaves the queue to the user.** After a cancel the TUI goes idle without submitting the queue head, even when the turn completed before the cancel landed. Esc on idle pops the most recent queued prompt into the textarea for editing, gated on the buffer being empty so a draft is never silently overwritten. The next submit joins the back of the queue and starts a turn with its head, so prompts keep the order they were typed in. A slash command that builds a prompt, such as `/init`, is the exception: its line is already in the chat, so it starts its own turn, and the queued prompts splice in behind it. A session switch discards queued prompts with a notice naming the count, since they were typed for the conversation that just ended. `/clear`, bare `/archive`, and `/resume` discard only the prompts queued before them and hold the input busy until the new session is ready, so a prompt typed meanwhile waits in the queue and runs in the new session. Esc during a switch cannot stop it, but leaves the waiting prompts to the user as after any cancel. `/compact` keeps the queue, because the conversation goes on from its summary.

6. **`App::status` is the one run state.** The variants (`Idle | Streaming | ToolRunning { name } | Compacting | SigningIn | SigningOut | Clearing | Resuming | Archiving | Cancelling | ExitArmed { until }`) live on `App`. `App::set_status` is the only way to change it, and it shows the new status in the status bar. The App itself routes Esc, Ctrl+C, and Ctrl+D, whose meaning depends on the status, and tells the input only whether to draw its busy rules, so no decision reads state back from a view. Stream and tool events go through `set_active_status`, which leaves a pending `Cancelling` in place until the turn's terminal event. `ExitArmed` needs no such guard, since only an idle input arms it and no stream or tool event arrives between turns (decision 8).

7. **Cancellation rides the existing `Event` channel.** `Event::Cancelled` covers both the TUI and `StdioSink`. No new event channel.

8. **Frontends end each operation on its terminal event.** Unless a shutdown stops it first, the engine ends each op with one terminal event, sent last, which the `protocol::Event` docs list per op. `Queue`, `Interrupt`, and `Resolve` act on the op in flight and have none of their own. `TurnEnd::of` maps an op and an event to how the op ended, counting `ConfigChanged` as a failure when the model has no level for an `/effort` pick, so the REPL and headless drivers stop rendering at the end of the op they sent, once nothing more of it can arrive. The TUI holds input from the start of a prompt, `/compact`, `/clear`, `/resume`, `/archive`, `/login`, or `/logout` until its terminal event, then runs the teardown that submits the queue head, so a queued prompt renders below the notices the new transcript raises. A failed `/resume` or `/archive` returns to idle with the queue still held, since its prompts were meant for the session it did not reach. `Error` reports failures that leave the operation running, such as a failed session write. `Notice` warns about a condition the session works around, such as drifted files, and `Retrying` is a dim notice for a request the client sends again.
