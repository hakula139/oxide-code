# Development

Learn how to set up the development environment, what the pre-commit hooks check, how the toolchain is pinned, how Nix and config files are styled, what debug info dev builds keep, what CI runs, and how to treat a failing check. For other ways to build `ox`, see [Installation](../guide/install.md).

## Dev Shell

The Nix flake provides the pinned Rust toolchain, `cargo-deny`, `cargo-insta`, `cargo-llvm-cov`, `cargo-mutants`, `git-cliff`, Node.js, and pnpm:

```bash
nix develop                                        # Dev shell with the Rust toolchain and pre-commit hooks
pnpm install                                       # Node-based formatters, linters, and spell checker
nix flake check                                    # Run pre-commit hooks
nix build '.#oxide-code'                           # Build ox from source
```

If you use [direnv](https://direnv.net), run `direnv allow` once. After that, `.envrc` loads the dev shell whenever you enter the repository.

## Pre-Commit Hooks

Entering the dev shell installs a [pre-commit](https://pre-commit.com) hook generated by [`git-hooks.nix`](https://github.com/cachix/git-hooks.nix). The shell generates its config, `.pre-commit-config.yaml`, as a gitignored symlink in each checkout, which is why [`AGENTS.md`](../../AGENTS.md#rules-for-every-change) asks for `nix develop -c true` in every new worktree.

The hook runs the compile-free subset of the [verification](../../AGENTS.md#verification) checks on staged files: file hygiene, Nix formatting and lints, `rustfmt`, Prettier and Taplo formatting, `markdownlint`, and `cspell`. Hooks that fix files in place fail the commit if they make changes, so stage the fixes and commit again. Checks that compile the workspace are excluded because their build cost would gate every commit.

The Node-based hooks run tools pinned in `node_modules` and fail when that directory is missing, so run `pnpm install` in each new checkout. `nix flake check` runs only the other hooks because its sandbox has no `node_modules`, while CI's Node Check job runs the Node tools. Run `pnpm format`, `pnpm lint`, and `pnpm spellcheck` directly when changing documentation, comments, or config files.

## Toolchain

- `rust-toolchain.toml` pins the exact Rust release used by the dev shell, CI, and release builds. The flake reads the pin through rust-overlay, while jobs outside Nix install it with `rustup toolchain install`.
- Renovate bumps the pin in its automerged flake-inputs group. If a new release adds lint failures, fix them in that PR so it can merge.
- `rust-version` in the root `Cargo.toml` sets the minimum supported Rust version for `cargo install` users. The MSRV job checks it, and [Versioning](../../RELEASING.md#versioning) explains how to bump it.

## Nix Style

`nixfmt` formats `flake.nix` and `package.nix`, and `statix` and `deadnix` lint them. These rules cover what the tools leave open:

- Keep code and comments within 100 columns, counting the indent. `nixfmt` does not reflow comments, so wrap them by hand.
- Mark the file header with `=` banners at column 0, and mark each section with `-` banners indented to match the code around them. Every banner line ends at column 100. A file without banners stays without them:

  ```nix
  # ==================================================================================================
  # oxide-code Development Flake
  # ==================================================================================================

          # ------------------------------------------------------------------------------------------
          # Dev Shell
          # ------------------------------------------------------------------------------------------
  ```

- Put each argument of a top-level function on its own line, even when the list would fit on one. Take `...` only when the caller passes a broader set, as with flake outputs. A `callPackage` derivation omits it, so an unexpected argument fails.
- Declare each dependency of a `callPackage` file, such as `package.nix`, as its own argument, as nixpkgs does, so `.override` can replace it. Put `lib` first and the other arguments in alphabetical order. In the flake, reach packages through `pkgs`.
- Put `inherit` entries first in a `let` block and in a call's argument set. In a set that returns data, keep each `inherit` where its entry belongs.
- Group related bindings and attributes, and order a `let` block so that each binding follows what it depends on. Within a group, use alphabetical order unless a stronger order applies.
- Follow a multiline binding or attribute with a blank line before its next sibling. Keep single-line siblings together and separate their groups with a blank line. A single-line binding may lead directly into a related multiline one.
- Write multiline text, such as a shell hook, as an indented string with literal line breaks.

## Config Style

Prettier and Taplo leave long strings alone, and no formatter covers shell code, so wrap YAML, TOML, and shell files by hand:

- Wrap comments at 100 columns, as [Writing](writing.md#comments) requires, and keep other lines within about 100, counting the indent. Leave a line long when it holds an unbreakable token, such as a URL or path, or sits in a heredoc body or literal block whose line breaks are content.
- Wrap a long string only where its value stays the same, and break it where [Rust](rust.md#strings) breaks a continued literal.
- Split a shell command that runs past the limit at its pipelines and `&&` or `||` lists, and split one in a Markdown code block the same way where that helps readability. If a part is still too long, keep at most what names the operation on its first line, such as the command, its subcommands, and a leading script, pattern, or message, and put each further flag with its value, or each group of related arguments, on a line of its own. Indent continuation lines one level past the first line, and end each line but the last with `\`, unless it ends with `|`, `&&`, or `||`, which already continue the command. In a workflow, write the command in a `run: |` block.

## Debug Info

Dev and test builds include line tables for the workspace crates and no debug info for dependencies, which limits the size of each checkout's `target/`. Panic messages keep their file and line, and so do backtrace frames in workspace code, while frames in dependency code may show only function names. To inspect variables in a debugger, set `CARGO_PROFILE_DEV_DEBUG=true` to rebuild the workspace crates with full debug info.

## CI

CI runs on pushes to `main`, pull requests, and manual dispatch, and the release workflow calls it again for each tag before publishing:

| Job              | Checks                                                                                                                           |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Nix Flake Check  | `nix flake check`, which runs the pre-commit hooks without the Node ones                                                         |
| Node Check       | `pnpm format`, `pnpm lint`, and `pnpm spellcheck`                                                                                |
| Rust Check       | `cargo fmt --all --check`, `cargo clippy --all-targets -- -D warnings`, `cargo clippy -- -D warnings`, and `cargo doc --no-deps` |
| Dependency Check | `cargo deny check licenses advisories sources bans`                                                                              |
| MSRV Check       | `cargo hack check --rust-version` against `rust-version`                                                                         |
| macOS Check      | Clippy, rustdoc, and the test suite on macOS                                                                                     |
| Windows Check    | Clippy, rustdoc, and the test suite on Windows                                                                                   |
| Coverage         | The test suite under `cargo llvm-cov`, uploaded to Codecov                                                                       |
| Nix Build        | The package build on Linux and macOS, which runs the tests and `ox --version`                                                    |

Branch protection requires only the CI Result job and Codecov's `codecov/patch` status. CI Result fails when any job in its `needs` fails or is cancelled, so list each new job there.

No job runs a plain `cargo build`, so run it locally for a quick compile check. See [RELEASING.md](../../RELEASING.md) for the release workflow.

## Failing Checks

Fix the cause of a failing hook, lint, test, or CI job. Skipped tests, `--skip` or `--exclude` flags, ignore and allowlist entries, `continue-on-error`, `|| true`, retries, and special cases for one path or commit only hide the failure. A test that cannot run in some environment, such as the Nix build sandbox, must be restructured until it can, as [Hermetic Tests](testing.md#hermetic-tests) describes.

Keep an ignore or allowlist entry only when it is the design, such as a license the project accepts, an advisory with no fix, or a generated file that a formatter must skip, and give the reason in the PR that adds it.
