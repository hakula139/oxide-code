# Development

Conventions for the dev shell, pre-commit hooks, toolchain, Nix and config file style, debug info, CI, and failing checks. For other ways to build `ox`, see [Installation](../guide/install.md).

## Dev Shell

The Nix flake provides the pinned Rust toolchain, `cargo-deny`, `cargo-insta`, `cargo-llvm-cov`, `cargo-mutants`, `git-cliff`, and the `sqlite3` shell:

```bash
nix develop                                        # Dev shell with the toolchain and hooks
nix develop -c run-hooks                           # Run shared formatting and lint hooks
nix flake check                                    # Run package, Home Manager, and overlay checks
nix build                                          # Build ox from source without running the tests
```

If you use [direnv](https://direnv.net), run `direnv allow` once. After that, `.envrc` loads the dev shell whenever you enter the repository, sources the gitignored `.envrc.local` when it exists, then loads the gitignored `.env.local`, so local setup and variables reach every command in the shell.

## Pre-Commit Hooks

Entering the dev shell in this repository installs a [pre-commit](https://pre-commit.com) hook generated by [`git-hooks.nix`](https://github.com/cachix/git-hooks.nix). The shell generates its config, `.pre-commit-config.yaml`, as a gitignored symlink in each checkout, which is why [`AGENTS.md`](../../AGENTS.md#rules-for-every-change) asks for `nix develop -c true` in every new worktree.

The hooks check file hygiene, Nix, shell, Nushell, Rust, GitHub Actions, web-format, TOML, Markdown, and spelling conventions. Rust formatting and Clippy use the same pinned toolchain as the dev shell. A hook that changes files fails the commit, so stage its fixes and commit again. A commit that touches Rust files runs Clippy over the whole workspace, and `nix develop -c run-hooks` runs every hook on all tracked files, as CI's Nix job does on Linux.

## Toolchain

- `rust-toolchain.toml` pins the exact Rust release used by the dev shell, the hooks, CI's Rust, Rust Lint, and Windows jobs, and release builds. The dev shell reads the pin through rust-overlay, while the Windows job and release builds install it with `rustup toolchain install`.
- The Nix package builds with the Rust release of the flake's pinned nixpkgs. Overlay and Home Manager consumers reuse that package output.
- Renovate bumps the pin in its automerged flake-inputs group. If a new release adds lint failures, fix them in that PR so it can merge.
- `rust-version` in the root `Cargo.toml` sets the minimum supported Rust version for `cargo install` and Nix users. The MSRV job builds the workspace with that release in the flake's `msrv` dev shell, the Nix jobs fail when it passes the Rust release of the flake's nixpkgs, and [Versioning](../../RELEASING.md#versioning) explains how to bump it.

## Nix Style

`nixfmt` formats `flake.nix` and the files in `nix/`, and `statix` and `deadnix` lint them. These rules cover what the tools leave open:

- Keep code within 100 columns, counting the indent, and wrap comments as [Writing](writing.md#comments) describes, since `nixfmt` does not reflow them.

- Mark the file header with `=` banners at column 0, and mark each section with `-` banners indented to match the code around them. Every banner line ends at column 100. A file without banners stays without them:

  ```nix
  # ==================================================================================================
  # oxide-code Development Flake
  # ==================================================================================================

          # ------------------------------------------------------------------------------------------
          # Dev Shell
          # ------------------------------------------------------------------------------------------
  ```

- Put each argument of a top-level function on its own line, even when the list would fit on one. Take `...` only when the caller passes a broader set, as with flake outputs. A `callPackage` derivation omits it, so an unexpected argument fails.

- Declare each dependency of a `callPackage` file, such as `nix/package.nix`, as its own argument, as nixpkgs does, so `.override` can replace it. Put `lib` first and the other arguments in alphabetical order. In the flake, reach packages through `pkgs`.

- Put `inherit` entries first in a `let` block and in a call's argument set. In a set that returns data, keep each `inherit` where its entry belongs.

- Group related bindings and attributes, and order a `let` block so that each binding follows what it depends on. Within a group, use alphabetical order unless a stronger order applies.

- Follow a multiline binding or attribute with a blank line before its next sibling. Keep single-line siblings together and separate their groups with a blank line. A single-line binding may lead directly into a related multiline one.

- Write multiline text, such as a shell hook, as an indented string with literal line breaks.

## Config Style

Prettier, Taplo, and shfmt format YAML, TOML, and shell files. Wrap comments and long strings by hand:

- Wrap comments as [Writing](writing.md#comments) describes, and keep other lines within about 100 columns, counting the indent. Leave a line long when it holds an unbreakable token, such as a URL or path, or sits in a heredoc body or literal block whose line breaks are content.
- Wrap a long string only where its value stays the same, and break it where [Rust](rust.md#strings) breaks a continued literal.
- Split a shell command that runs past the limit at its pipelines and `&&` or `||` lists, and split one in a Markdown code block the same way where that helps readability. If a part is still too long, keep at most what names the operation on its first line, such as the command, its subcommands, and a leading script, pattern, or message, and put each further flag with its value, or each group of related arguments, on a line of its own. Indent continuation lines one level past the first line, and end each line but the last with `\`, unless it ends with `|`, `&&`, or `||`, which already continue the command. In a workflow, write the command in a `run: |` block.
- For a multiline command substitution, put the command on the next line and the closing `)` on its own line, aligned with the assignment.

## Debug Info

Dev and test builds include line tables for the workspace crates and no debug info for dependencies, which limits the size of each checkout's `target/`. Panic messages keep their file and line, and so do backtrace frames in workspace code, while frames in dependency code may show only function names. To inspect variables in a debugger, set `CARGO_PROFILE_DEV_DEBUG=true` to rebuild the workspace crates with full debug info.

## CI

CI runs on pushes to `main`, pull requests, and manual dispatch. The release workflow publishes a tag only after a push or dispatched CI run on the tagged commit passes, and calls CI itself for a dry run from another ref:

| Job                            | Checks                                                                                                                                                             |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Nix (Linux, macOS)             | Package build and version check, Home Manager and overlay checks, plus all hooks on Linux (including Rust formatting and Clippy) and dev-shell hook tools on macOS |
| Rust Check (Linux, macOS)      | `cargo clippy --all-targets` on macOS, the test suite under `cargo llvm-cov`, uploaded to Codecov, and the doc tests                                               |
| MSRV Check                     | `cargo check --all-targets` in the flake's `msrv` shell                                                                                                            |
| Rust Lint Check (Linux, macOS) | `cargo clippy` without test targets and `cargo doc --no-deps`, then on Linux a check that every snapshot baseline has a test                                       |
| Windows Check                  | `cargo clippy --all-targets`, `cargo clippy`, `cargo doc --no-deps`, and the test suite under `cargo llvm-cov`, uploaded to Codecov                                |
| Dependency Check               | `cargo deny check` in the flake's `lint` shell, which leaves out the pinned toolchain                                                                              |

The Nix, Rust, and MSRV jobs come from devkit's [reusable workflows](https://github.com/hakula139/devkit/blob/v3/docs/ci.md), and the Rust Lint job runs the checks `rust.yml` leaves out.

Branch protection requires only the CI Result job and Codecov's `codecov/patch` status. CI Result reads every attempt's jobs from the Actions API, keeps the latest attempt for each job name, and fails when any job of the CI workflow, including each matrix leg, concludes anything other than success or skipped. That catches a leg cancelled before a runner picks it up, which the `needs` results of a matrix job omit, and retains earlier failures when only the gate reruns. CI Result runs once the jobs in its `needs` finish, even after a failure, since a skipped required check passes. It skips any job still running, so list each new job in its `needs`, or a job that finishes after the gate goes unchecked.

Every job but Windows and CI Result pulls from the `hakula` Cachix cache and pushes its builds only on the default branch. The cache only saves build time, so a failed Cachix setup, download, or push does not fail a job: a failed setup logs a warning and the job builds without the cache, a failed download makes Nix build that path from source, and a failed push at the end of the job shows Cachix's error annotation on a green job. Every other failed step still fails its job and CI Result. A download that stalls without failing still runs the job into its timeout, which [#715](https://github.com/hakula139/oxide-code/issues/715) tracks.

A push to a pull request cancels the CI it supersedes, while every push to `main` gets its own run, which a later push never cancels.

Each job sets `timeout-minutes` to several times its usual duration, so a hung test stops its job at that limit, where it would otherwise hold the runner for GitHub's six-hour default. GitHub reports such a job as cancelled, with an annotation saying it exceeded the maximum execution time, and CI Result counts it as a failure. Give each new job a limit the same way. libtest names any test still running after 60 seconds, so the log of a timed-out job shows which test hung.

No job runs a plain `cargo build`, so run it locally for a quick compile check. See [RELEASING.md](../../RELEASING.md) for the release workflow.

## Failing Checks

Fix the cause of a failing hook, lint, test, or CI job. Skipped tests, `--skip` or `--exclude` flags, ignore and allowlist entries, `continue-on-error`, `|| true`, retries, and special cases for one path or commit only hide the failure. A test that cannot run in some environment, such as Windows, must be restructured until it can, as [Hermetic Tests](testing.md#hermetic-tests) describes.

Keep an ignore or allowlist entry only when it is the design, such as a license the project accepts, an advisory with no fix, or a generated file that a formatter must skip. Keep a `continue-on-error` only on a step whose failure cannot change what a build or check finds, such as the Cachix setup. Give the reason in the PR that adds either.
