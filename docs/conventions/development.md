# Development

Conventions for the dev shell, pre-commit hooks, toolchain, Nix and config file style, debug info, CI, and failing checks. For other ways to build `ox`, see [Installation](../guide/install.md).

## Dev Shell

The Nix flake provides the pinned Rust toolchain, `cargo-deny`, `cargo-insta`, `cargo-llvm-cov`, `cargo-mutants`, `git-cliff`, Node.js, pnpm, and the `sqlite3` shell:

```bash
nix develop                                        # Dev shell with the toolchain, hooks, and Node tools
nix flake check                                    # Run most hooks, the module tests, and the test suite
nix build                                          # Build ox from source without running the tests
```

If you use [direnv](https://direnv.net), run `direnv allow` once. After that, `.envrc` loads the dev shell whenever you enter the repository, sources the gitignored `.envrc.local` when it exists, then loads the gitignored `.env.local`, so local setup and variables reach every command in the shell.

## Pre-Commit Hooks

Entering the dev shell in this repository installs a [pre-commit](https://pre-commit.com) hook generated by [`git-hooks.nix`](https://github.com/cachix/git-hooks.nix). The shell generates its config, `.pre-commit-config.yaml`, as a gitignored symlink in each checkout, which is why [`AGENTS.md`](../../AGENTS.md#rules-for-every-change) asks for `nix develop -c true` in every new worktree.

The hook runs the compile-free subset of the [verification](../../AGENTS.md#verification) checks on staged files: file hygiene, Nix formatting and lints, ShellCheck, `rustfmt`, Prettier and Taplo formatting, `markdownlint`, and `cspell`, plus a `comment-width` check. Hooks that fix files in place fail the commit if they make changes, so stage the fixes and commit again. Checks that compile the workspace are excluded because their build cost would gate every commit.

The Node-based hooks run tools pinned in `node_modules`, which pnpm installs before running them whenever it is missing or out of date with the lockfile. `nix flake check` leaves them out because its sandbox cannot install `node_modules`, and it leaves out `rustfmt` so that it never fetches the pinned toolchain. CI's Lint job runs the Node tools, and its Rust (Linux) job runs `cargo fmt --check`. Run `pnpm format`, `pnpm lint`, and `pnpm spellcheck` directly when changing documentation, comments, or config files.

## Toolchain

- `rust-toolchain.toml` pins the exact Rust release used by the dev shell, CI, and release builds. The dev shell reads the pin through rust-overlay, while jobs outside Nix install it with `rustup toolchain install`.
- The Nix package and its `tests` check build with the Rust release of the nixpkgs they come from, so a consumer that follows its own nixpkgs never fetches the pinned toolchain.
- Renovate bumps the pin in its automerged flake-inputs group. If a new release adds lint failures, fix them in that PR so it can merge.
- `rust-version` in the root `Cargo.toml` sets the minimum supported Rust version for `cargo install` and Nix users. The MSRV job checks it, the Nix jobs fail when it passes the Rust release of the flake's nixpkgs, and [Versioning](../../RELEASING.md#versioning) explains how to bump it.

## Nix Style

`nixfmt` formats `flake.nix` and the files in `nix/`, and `statix` and `deadnix` lint them. These rules cover what the tools leave open:

- Keep code within 100 columns, counting the indent, and wrap comments as [Writing](writing.md#comments) describes, since `nixfmt` does not reflow them.
- Mark the file header with `=` banners at column 0, and mark each section with `-` banners indented to match the code around them. Every banner line ends at column 100. A file without banners stays without them:

  ```nix
  # ==================================================================================================
  # oxide-code Development Flake
  # ==================================================================================================

          # ------------------------------------------------------------------------------------------
          # Dev Shell
          # ------------------------------------------------------------------------------------------
  ```

- Put each argument of a top-level function on its own line, even when the list would fit on one. Take `...` only when the caller passes a broader set, as with flake outputs. A `callPackage` derivation omits it, so an unexpected argument fails.
- Declare each dependency of a `callPackage` file, such as `nix/package.nix`, as its own argument, as nixpkgs does, so `.override` can replace it. Put `lib` first and the other arguments in alphabetical order. In the flake, reach packages through `pkgs`.
- Put `inherit` entries first in a `let` block and in a call's argument set. In a set that returns data, keep each `inherit` where its entry belongs.
- Group related bindings and attributes, and order a `let` block so that each binding follows what it depends on. Within a group, use alphabetical order unless a stronger order applies.
- Follow a multiline binding or attribute with a blank line before its next sibling. Keep single-line siblings together and separate their groups with a blank line. A single-line binding may lead directly into a related multiline one.
- Write multiline text, such as a shell hook, as an indented string with literal line breaks.

## Config Style

Prettier and Taplo leave long strings alone, and no formatter covers shell code, so wrap YAML, TOML, and shell files by hand:

- Wrap comments as [Writing](writing.md#comments) describes, and keep other lines within about 100 columns, counting the indent. Leave a line long when it holds an unbreakable token, such as a URL or path, or sits in a heredoc body or literal block whose line breaks are content, unless it starts with `#`, which the `comment-width` hook checks as a comment.
- Wrap a long string only where its value stays the same, and break it where [Rust](rust.md#strings) breaks a continued literal.
- Split a shell command that runs past the limit at its pipelines and `&&` or `||` lists, and split one in a Markdown code block the same way where that helps readability. If a part is still too long, keep at most what names the operation on its first line, such as the command, its subcommands, and a leading script, pattern, or message, and put each further flag with its value, or each group of related arguments, on a line of its own. Indent continuation lines one level past the first line, and end each line but the last with `\`, unless it ends with `|`, `&&`, or `||`, which already continue the command. In a workflow, write the command in a `run: |` block.
- For a multiline command substitution, put the command on the next line and the closing `)` on its own line, aligned with the assignment.

## Debug Info

Dev and test builds include line tables for the workspace crates and no debug info for dependencies, which limits the size of each checkout's `target/`. Panic messages keep their file and line, and so do backtrace frames in workspace code, while frames in dependency code may show only function names. To inspect variables in a debugger, set `CARGO_PROFILE_DEV_DEBUG=true` to rebuild the workspace crates with full debug info.

## CI

CI runs on pushes to `main`, pull requests, and manual dispatch, and the release workflow calls it again for each tag before publishing:

| Job                          | Checks                                                                                                                                                                 |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Lint                         | `pnpm format`, `pnpm lint`, `pnpm spellcheck`, and `cargo deny check` in the flake's `lint` shell, which leaves out the pinned toolchain                               |
| Rust (Linux, macOS, Windows) | `cargo fmt --check` on Linux, then `cargo clippy --all-targets`, `cargo clippy`, `cargo doc --no-deps`, and the test suite under `cargo llvm-cov`, uploaded to Codecov |
| MSRV                         | `cargo hack check --rust-version` against `rust-version`                                                                                                               |
| Nix (Linux, macOS)           | `nix flake check`, which also runs the test suite in the build sandbox, then the package build with its `ox --version` and installed license notice checks             |

Branch protection requires only the CI Result job and Codecov's `codecov/patch` status. CI Result reads every job of the current run attempt from the Actions API and fails when any job of the CI workflow, including each matrix leg, concludes anything other than success or skipped. That catches a leg cancelled before a runner picks it up, which the `needs` results of a matrix job omit. CI Result runs once the jobs in its `needs` finish and counts any unfinished job as a failure, so list each new job there.

A push to a pull request cancels the CI it supersedes, while every push to `main` gets its own run, which a later push never cancels.

Each job sets `timeout-minutes` to several times its usual duration, so a hung test stops its job at that limit, where it would otherwise hold the runner for GitHub's six-hour default. GitHub reports such a job as cancelled, with an annotation saying it exceeded the maximum execution time, and CI Result counts it as a failure. Give each new job a limit the same way. libtest names any test still running after 60 seconds, so the log of a timed-out job shows which test hung.

No job runs a plain `cargo build`, so run it locally for a quick compile check. See [RELEASING.md](../../RELEASING.md) for the release workflow.

## Failing Checks

Fix the cause of a failing hook, lint, test, or CI job. Skipped tests, `--skip` or `--exclude` flags, ignore and allowlist entries, `continue-on-error`, `|| true`, retries, and special cases for one path or commit only hide the failure. A test that cannot run in some environment, such as the Nix build sandbox, must be restructured until it can, as [Hermetic Tests](testing.md#hermetic-tests) describes.

Keep an ignore or allowlist entry only when it is the design, such as a license the project accepts, an advisory with no fix, or a generated file that a formatter must skip, and give the reason in the PR that adds it.
